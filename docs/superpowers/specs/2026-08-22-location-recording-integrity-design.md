# GPS記録の吸着状態永続化・距離更新整合性 設計

## 1. 背景

滞在ポイントを設定した場所から動いていない日について、日別詳細画面の移動距離が83.37kmと表示された。対象日のGPXを調査したところ、次の特徴を確認した。

- 7,106ポイントが記録されていた
- GPXの時系列座標から算出した総距離は約5.70kmだった
- 座標範囲は約104m × 98mに収まっていた
- 最大隣接区間は約42.8mで、数十kmの位置飛びは存在しなかった

したがって、83.37kmはGPXに含まれる生座標の移動ではなく、端末内で保存された日別距離の累積処理によって生じた値と判断する。

現在の実装には次の整合性上の問題がある。

1. バックグラウンド位置情報コールバックごとに `LocationRecordingSession` を作り直すため、滞在ポイントへの入場・退出を判定する3点連続の状態が失われる。
2. 前景と背景は別々のセッション状態を持つため、切替時に吸着状態が一致しない可能性がある。
3. `insertLocationPoint` は排他トランザクションを開始する前に同日の最新点を読み、区間距離を計算する。複数の保存処理が重なると、同じ直前点を基準に複数回加算できる。
4. 日別距離は `daily_logs.distance_meters` に累積保存され、日別詳細・ODO実績などから利用される。保存後の値を表示時にGPX座標から再計算する設計ではない。

## 2. 目的

- 前景・背景・JSプロセス再生成をまたいで滞在ポイントの吸着状態を維持する。
- バックグラウンド配信が1観測ずつに分かれても、50m以内の3点目から中心座標へ吸着する。
- 前景・背景の保存が競合しても、GPS点、日別距離、Visited Gridを一貫した状態で更新する。
- 時系列の途中へ点が挿入されても、日別距離へ正しい差分だけを加える。
- 既存の距離・実績は変更せず、アップデート後の新しい観測から修正を適用する。

## 3. 非目的

- 既存の `daily_logs.distance_meters` を再計算・修復しない。
- `achievement_unlocks`、実績通知、解除済み実績を変更・削除しない。
- 過去GPXから有効座標や吸着履歴を復元しない。
- 設定画面へ距離再計算ボタンを追加しない。
- GPXインポートの距離集計方式は変更しない。
- 位置情報品質フィルターや滞在ポイントの50m・3点連続という判定条件は変更しない。

既存距離を修復すると、解除済み実績は維持される一方で現在距離との不整合が生じる可能性がある。このため、本対応は将来の記録だけを正す。

## 4. 採用方式

### 4.1 比較した方式

#### A. 永続的な記録状態と原子的な更新

吸着状態をSQLiteへ保存し、1観測の記録に必要な更新を同じ排他トランザクションへまとめる。

- OSやJSプロセスのライフサイクルに依存しない。
- 前景・背景で同じ状態を共有できる。
- DB競合時に部分的な更新を残さない。
- 新しいテーブルと記録パイプラインの再構成が必要になる。

#### B. プロセス内の共有セッション

モジュール内の単一セッションとキューを前景・背景から共有する。

- 変更は比較的小さい。
- OSがJSプロセスを終了すると状態を失い、バックグラウンド吸着を保証できない。

#### C. 距離更新のみ原子的にする

日別距離の競合だけを修正し、吸着状態はセッション内に残す。

- 異常な重複加算は抑制できる。
- バックグラウンドで吸着しない問題が残る。

### 4.2 決定

方式Aを採用する。吸着状態は保存対象外になった観測も含めて連続点数を数えるため、保存済みGPS点だけから正確に復元できない。専用状態を永続化し、前景・背景を同じ記録境界へ統合する。

## 5. データモデル

### 5.1 `location_recording_state`

吸着判定に必要な現在状態を単一行で保存する。

| 列名                            | 型      | 制約・意味                                                       |
| ------------------------------- | ------- | ---------------------------------------------------------------- |
| `id`                            | INTEGER | PRIMARY KEY。常に `1`                                            |
| `active_stay_place_id`          | INTEGER | 現在吸着中の滞在ポイントID。未吸着ならNULL                       |
| `candidate_stay_place_id`       | INTEGER | 入場判定中の候補ID。候補なしならNULL                             |
| `candidate_count`               | INTEGER | 同じ候補が50m以内に入った連続観測数                              |
| `outside_count`                 | INTEGER | 吸着先から50m外になった連続観測数                                |
| `last_observed_at`              | TEXT    | 状態へ反映した最後の観測日時。初期状態ではNULL                   |
| `last_visited_grid_recorded_at` | TEXT    | 最後にVisited Gridへ反映した有効座標の観測日時。初期状態ではNULL |
| `last_visited_grid_latitude`    | REAL    | 最後にVisited Gridへ反映した有効緯度。初期状態ではNULL           |
| `last_visited_grid_longitude`   | REAL    | 最後にVisited Gridへ反映した有効経度。初期状態ではNULL           |
| `updated_at`                    | TEXT    | 状態行の最終更新日時                                             |

滞在ポイントIDには外部キーを設定しない。滞在ポイント削除、Plus解約、無料版の有効対象変更によりIDが無効になった場合は、次に有効な滞在ポイント一覧を取得できた観測で既存のresolver規則に従って解除する。

テーブル作成時に既存の `location_points`、`daily_logs`、`achievement_unlocks` は更新しない。状態行は最初の観測を処理するときに初期値から作成する。既存端末には3つのVisited Grid補間列を `ensureColumn` で冪等に追加し、過去の保存点から埋め戻さない。

Visited Grid補間用の3列は、最後にセル更新へ利用できた有効座標を一組として扱う。いずれかがNULLまたは不正値なら補間起点なしとして安全側へ倒し、現在観測のセルだけを処理する。

「すべてのデータを削除」では状態行も削除する。次の観測時には未吸着状態から開始する。

## 6. コンポーネント境界

### 6.1 吸着resolver

`stayPlaceSnapResolver.ts` は純粋関数のまま維持する。SQLite行と `StayPlaceSnapState` の変換は記録状態リポジトリで行い、resolverへDB依存を持ち込まない。

### 6.2 記録状態リポジトリ

`location_recording_state` の読取・更新を担当する。呼び出し元の排他トランザクションを受け取り、独自にトランザクションを開始しない。

### 6.3 原子的な観測記録サービス

1件の観測について、次の処理を1つの排他トランザクション内で実行する。

1. 永続化された吸着状態を読む。
2. 信頼できる `last_observed_at` 以前の古い観測なら、状態とGPSログへ反映せず終了する。永続値が処理時刻より1時間を超えて未来の場合は端末時計の巻き戻りとみなし、このガードだけを無効として処理を継続する。
3. 生座標と有効な滞在ポイントから吸着結果を求める。
4. 有効座標と直前の保存済み有効座標を使って保存判定を行う。
5. 永続状態の直前セル開放対象点と現在の有効観測からVisited Gridを求め、GPSログの保存対象外でも同じトランザクションで更新する。
6. セル更新に利用できた観測では、Visited Grid補間起点も現在の有効座標と観測日時へ更新する。
7. 保存対象外でも吸着状態、`last_observed_at`、Visited Grid補間起点を更新する。
8. 保存対象なら `location_points` へ挿入する。一意制約 `(recorded_at, latitude, longitude)` の競合だけを既存データ優先で無視し、NOT NULLなど他の制約違反は例外としてロールバックする。
9. 時系列上の直前点と直後点を順番に取得し、日別距離の追加差分を求める。
10. `daily_logs` の点数、開始・終了時刻、距離を更新する。既存の `distance_meters` がNULLなら、部分差分へ変換せずNULLを維持する。
11. 吸着状態とVisited Grid補間起点を保存して確定する。

GPS点の一意制約に一致する重複観測、または信頼できる `last_observed_at` 以前の観測では、吸着連続点数、Visited Grid補間起点、日別集計を更新しない。同じGPS観測の再配信だけで3点連続を満たさないため、重複観測を保存対象外の新規観測と同一視しない。

### 6.4 セッション

`LocationRecordingSession` はセッション内の吸着状態を正とせず、次のオーケストレーションだけを担当する。

- GPXインポート優先中のバッファリング
- バッチ内観測の日時昇順ソート
- バッチ単位の有効滞在ポイント取得
- 観測単位の原子的記録サービス呼び出し
- 保存確定後の実績処理
- 失敗した未処理観測の再キュー

Visited Grid補間用の直前点は `location_recording_state` を正とし、観測ごとの排他トランザクション内で読み書きする。これにより、GPSログの保存対象外になった観測を挟んで別の前景・背景セッションへ切り替わっても、実際に通過していないセルを古い保存点から補間しない。この値は吸着判定や日別距離の正にはしない。

前景と背景は同じサービスを通るため、別セッションであってもSQLiteの吸着状態とVisited Grid補間起点を共有する。`backgroundLocationTask` がコールバックごとにセッションを生成しても、どちらの状態も失われない。保存判定に使う最新保存点はセッション開始時ではなく、観測ごとの排他トランザクション内で取得する。

### 6.5 GPSログリポジトリ

ライブGPS点の挿入は、呼び出し元の排他トランザクションを受け取る `insertLocationPointInCurrentTransaction` へ一本化する。本番の呼び出し元がない単発トランザクション用ラッパー `insertLocationPoint` は削除し、例外契約が異なる未使用APIを残さない。

挿入結果の `changes` が取得できない場合は挿入成功と推測せず、日別集計を更新しない安全側へ倒す。前後点は同じSQLite runnerから逐次取得し、同一トランザクション内のステートメント順序を明確にする。時系列途中への挿入はライブ観測の単調増加ガードでは通常到達しないが、将来のトランザクション内利用でも集計を壊さない安全網として維持する。

## 7. 距離更新

### 7.1 通常の時系列追加

同日の末尾へ新しい点 `N` を追加する場合は、直前点 `P` との距離を加える。既存の `daily_logs.distance_meters` がNULLなら表示側で全点から再計算する契約を維持するため、NULLのまま保持する。

```text
追加距離 = distance(P, N)
```

同日の最初の点なら追加距離は0とする。

### 7.2 時系列途中への挿入

時系列上の直前点 `P` と直後点 `S` の間へ `N` を追加する場合、既存集計には `P → S` が含まれているため、次の差分だけを加える。

```text
追加距離 = distance(P, N) + distance(N, S) - distance(P, S)
```

先頭へ追加し直後点だけがある場合は `distance(N, S)` を加える。浮動小数点誤差による微小な負値は0へ丸める。

前後点の検索、GPS点挿入、日別集計更新を同じ排他トランザクションで行う。これにより、前景・背景が同じ直前点を読んで重複加算する競合を防ぐ。

距離計算には従来どおり有効座標を使う。吸着済み点では滞在ポイント中心、未吸着点では生座標となる。

## 8. 観測順序

- Expoから1回に複数観測が届いた場合は `recordedAt` の昇順に並べる。
- 永続状態の信頼できる `last_observed_at` と同時刻またはそれ以前の観測は、ライブ記録では保存しない。
- `last_observed_at` が処理時刻より1時間を超えて未来なら、端末時計の巻き戻りで記録が恒久停止しないようガードを無効として扱い、次の正常観測で上書きする。
- 古い観測で入場・退出カウンターを巻き戻さない。
- GPXインポートは独立した既存経路を使うため、このライブ観測順序制約の対象外とする。

現行の保存フィルターも非正の時間差を保存しないため、古いライブ観測を除外する方針は既存意図と一致する。

## 9. 滞在ポイント取得失敗

滞在ポイントまたは課金状態の取得に一時的に失敗しても、GPS記録自体は停止しない。

- 当該観測は生座標として保存判定する。
- 永続化済みの吸着状態は変更しない。
- `last_observed_at` は更新し、同じ観測の再処理で連続点数を重複させない。
- 次に有効一覧を取得できた観測から、保存済み状態を使って吸着判定を再開する。

この場合は中心と生座標の一時的な差が記録される可能性がある。ただし距離更新は原子的に行われるため、同一区間の多重加算は起こらない。

## 10. エラー処理

吸着状態、GPS点、日別集計、Visited Grid、補間起点のいずれかの更新に失敗した場合は、排他トランザクション全体をロールバックする。GPS点の重複以外の制約違反も握りつぶさず、この失敗経路へ合流させる。セッションは失敗した観測を含む未処理分を既存バッファへ戻し、次回の位置更新時に再試行する。

トランザクション確定後の実績処理は従来どおり独立して実行する。逆ジオコーディングや通知処理の失敗で、確定済みGPS点と距離を巻き戻さない。

## 11. 既存データと実績

本対応のマイグレーションは新しい状態テーブルを作るだけであり、既存集計を修復しない。

- `daily_logs.distance_meters` を再計算しない。
- 既存の83.37kmなど、すでに累積された値は維持する。
- `achievement_unlocks` と `achievement_notification_queue` を変更しない。
- 解除済み実績を取り消さない。
- 未解除実績の進捗も、既存集計値を含む現在の計算方式を維持する。

アップデートした当日は、既存の日別距離へ修正後の新規区間が加算される。完全に修正後の記録だけで構成されるのは、原則としてアップデート後に始まる新しい日付からとなる。

## 12. テスト方針

### 12.1 純粋ロジック

- SQLite行と吸着状態を相互変換できる。
- 直前点のみ、直後点のみ、前後点ありの距離差分を計算できる。
- 浮動小数点誤差による負の差分を0へ丸める。
- バッチ内観測を安定して時刻順へ並べる。

### 12.2 リポジトリ・トランザクション

- 初回観測で単一状態行を作成する。
- 既存端末へVisited Grid補間列を冪等に追加し、既存距離や実績を更新しない。
- 保存対象外の観測でも吸着状態を更新する。
- GPS点保存時に状態、日別集計、Visited Gridを同じトランザクションで更新する。
- GPSログの保存対象外でも、吸着状態とVisited Gridを同じトランザクションで更新する。
- 重複・古い観測で状態と距離を二重更新しない。
- 別セッション間の保存対象外観測を永続補間起点として引き継ぐ。
- 未来へ進みすぎた永続観測日時があっても、正常時刻の観測で記録を再開する。
- GPS点の一意制約だけを既存データ優先とし、他の制約違反は例外として伝播する。
- 既存の日別距離がNULLの場合はNULLを維持する。
- 時系列途中への挿入で置換差分だけを加える。
- 途中失敗時に部分更新が確定しない。
- マイグレーションが既存距離と実績テーブルへUPDATEを行わない。

JestではSQLiteをモックするため、実際のロック・ロールバックはiOS・Android実機でも確認する。

### 12.3 セッション統合

- 1件ずつ分かれた3回の背景コールバックで3点目から吸着する。
- セッションを再生成しても入場・退出カウンターとVisited Grid補間起点を引き継ぐ。
- 前景から背景へ切り替えても同じ吸着状態を使う。
- 保存されない細かな観測も3点連続の判定へ含める。
- 有効滞在ポイント取得失敗時は生座標を使い、吸着状態を維持する。
- Plus解約または滞在ポイント削除後、次の正常取得時に無効な吸着を解除する。
- 自宅付近の密集観測を複数コールバックへ分割した回帰ケースで、異常な距離増加が起きない。
- GPXインポートの既存テストが引き続き通る。

回帰データは調査対象GPXそのものをコミットせず、座標範囲・観測密度・コールバック分割を再現した小さな合成フィクスチャを使用する。

### 12.4 実機確認

iOSとAndroidで次を確認する。

1. 滞在ポイント内で前景記録を開始し、3点目から中心へ吸着する。
2. 画面消灯・バックグラウンド移行後も中心への吸着を維持する。
3. アプリまたはJSプロセス相当の再生成後も吸着を維持する。
4. 50m外の1〜2点では維持し、3点連続で退出する。
5. 長時間静止しても日別距離が異常増加しない。
6. Plus解約時は無料版で有効な1件だけが吸着対象になる。
7. GPXインポート、日別画面、実績画面の既存表示が変わらない。
