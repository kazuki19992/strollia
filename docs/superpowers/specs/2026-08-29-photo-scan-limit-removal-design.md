# 写真マップ Phase 2-c: 表示上限の撤廃と同期モデルの見直し 設計書

作成日: 2026-08-29

親設計書: `docs/superpowers/specs/2026-08-10-photo-map-scan-limit-removal-design.md`
（本書は親設計書の §4.0 / §4.2 / §8 を**実測に基づいて置き換える**）

関連: PR #146（2-a）/ #162（2-b）/ #165（サムネイル）/ #167（新API移行）

## 1. 目的

写真表示の 200件上限を撤廃する。あわせて、走査と表示の関係を実測に基づいて設計し直す。

## 2. 実測値: 親設計書の前提は約40倍外れていた

実機（iPhone、写真 18,218枚）での計測結果。

| 走査上限 | 走査件数 | ジオタグ | メタデータ | 位置取得 | 保存 | 合計  |
| -------- | -------- | -------- | ---------- | -------- | ---- | ----- |
| 200      | 200      | 127      | 0.4s       | 0.2s     | 0.0s | 0.6s  |
| 1,000    | 1,000    | 476      | 0.5s       | 1.1s     | 0.1s | 1.6s  |
| 3,000    | 3,000    | 1,104    | 0.6s       | 3.2s     | 0.1s | 3.9s  |
| 20,000   | 17,988   | 1,400    | 1.4s       | 21.9s    | 0.2s | 23.6s |

読み取れること。

- **全ライブラリ走査が 24秒**。親設計書 §3.1 の「1万枚で約8分（480秒）」に対し、1万枚換算で約13秒。**約40倍の乖離**
- **位置取得が支配的**（合計の93%）。1枚あたり約1.1msでほぼ完全に線形。5万枚なら約60秒と外挿できる
- **メタデータはほぼ固定コスト**（0.4s→1.4s）。`exeForMetadata()` のバッチ取得が効いている
- **保存は無視できる**（1,400件で0.2s）。ボトルネックにならない
- **古い写真ほどジオタグ率が低い**（最新200件で63.5% → 全体で7.8%）。3,000件目より古い14,988枚のうちジオタグ付きは296枚だけ

親設計書の「ブロッキングダイアログでアプリを止めて数分待たせる」という UX 設計は、
**この試算だけを根拠にしていた**。前提が消えたため設計をやり直す。

### 2.1 走査中に地図を操作すると遅くなる

同じ全件走査で、読み込み中に地図をパン・ズームした場合は **合計 38.7秒**（位置取得 31.7秒）。
走査していない場合の 23.6秒に対して **1.6倍**。

ビューポート検索とサムネイル解決が `getLocation()` と同じスレッド・ネイティブリソースを取り合うため。
この事実は §4.4 のブロッキング判断の根拠になる。

## 3. 現状の問題

実測の過程で、実装と仕様の食い違いが見つかった。

1. **走査が毎起動フルで走る。** `usePhotoMapOverlay` の `assetSyncPromiseRef` は React の ref で、
   アプリ再起動で消える。DBキャッシュの有無を見ておらず、起動のたびに全件走査している
2. **`docs/photo-geotag.md` §8 の記述が実態と違う。** 「2回目以降の起動では走査なしで地図に写真を出せる」
   とあるが未実装
3. **キャッシュを走査完了まで使わない。** `loadPhotosForRegion` は `await syncPhotoAssets()` のあとに
   ビューポート検索を行う。DBに写真があるのに、起動後 24〜39秒間なにも表示されない
4. **ビューポート検索に `LIMIT` が無い**（PR #162 の申し送り事項）
5. **サムネイル解決が「範囲内の全写真」に走る。** 地図に見えるのはクラスタの代表1枚だけなのに、
   `+187` のクラスタなら188枚ぶん生成している

## 4. 方針

### 4.1 走査と表示を分離する

|          | 対象                       | 決めるもの                             |
| -------- | -------------------------- | -------------------------------------- |
| **走査** | 常に写真ライブラリ全体     | 削除検知の正確さ。ユーザーには見えない |
| **表示** | `photo_assets` から最新N件 | ユーザー設定（§4.6）                   |

この分離により、設定の説明から「最新N件の**うちジオタグ付き**」という回りくどさが消える。
`photo_assets` にはジオタグ付き写真しか入らないので、`ORDER BY taken_at DESC LIMIT N` が
そのまま「最新N件のジオタグ写真」になる（`idx_photo_assets_taken_at` は作成済み）。

### 4.2 キャッシュ先読み（最優先）

写真表示の有効化・アプリ起動時は、**走査を待たずに `photo_assets` から表示する**。
走査はその後ろで走らせ、完了したら表示を更新する。

これが入ると、走査に24秒かかること自体がユーザーから見えなくなる。§3 の問題3の解消でもある。

### 4.3 差分スキャン（自動・軽量）

自動で走る走査は**前回の走査時点より新しい写真だけ**を対象にする（`Query.gt(CREATION_TIME, …)`）。
前回走査の基準時刻は `app_settings` に保存する。

- 通常は数件〜数十件なので、体感コストはほぼゼロ
- 走査済み時間窓の突き合わせ（PR #162）はそのまま働き、**新しい範囲の削除は検知される**
- 古い範囲の削除は検知しない。これは §4.5 の導線で回収する

**AirDrop やインポートで後から入った古い写真は取りこぼす。** 全件スキャン（§4.4）で回収する。

### 4.4 全件スキャン（明示操作のみ・ブロッキング）

全件スキャンはユーザーが明示的に指示したときだけ実行する。導線は2つ。

- 設定画面の「ライブラリを再読み込み」
- 削除済み写真ダイアログの「ライブラリを再読み込み」（§4.5）

**実行中はダイアログで他の操作をブロックする。** §2.1 のとおり、走査中に地図を操作すると
競合で1.6倍遅くなる。操作させないことで**結果的に早く終わる**。

親設計書のブロッキングダイアログは「不要」ではなく、**適用範囲が変わった**。
自動走査には不要で、明示的な全件スキャンにだけ使う。

ダイアログには進捗を出す。`exeForMetadata()` の完了後は総数が分かるため「N件中M件」を表示できる。
それ以前は不定形の表示にする。

### 4.5 削除済み写真の検知と再読み込み導線

差分スキャンでは古い範囲の削除を検知できないため、削除済み写真の行が残りうる。

**サムネイルの見え方は状況で変わる。**

| 状況                         | 見え方                                                             |
| ---------------------------- | ------------------------------------------------------------------ |
| 同一セッション中に削除された | メモリキャッシュと生成済みファイルが残るため、サムネイルが出続ける |
| アプリ再起動後               | 再解決に失敗し、画像なしプレースホルダになる                       |

どちらでもマーカーは地図に残るため、**拡大表示しようとした時点**で気づける。

#### 存在確認を分ける

画像を取得できない原因は2つあり、**区別しないと誤案内になる**。

| 原因                                            | 再読み込みで解決するか |
| ----------------------------------------------- | ---------------------- |
| 写真ライブラリから削除された                    | する                   |
| iCloud にあり端末未ダウンロード（オフライン等） | **しない**             |

`modules/photo-thumbnail/` に**アセットの存在確認**を追加する。
`PHAsset.fetchAssets(withLocalIdentifiers:)` の結果が空かどうかを見るだけで、I/O もデコードも不要。

#### 削除済みの場合のダイアログ

- タイトル: **削除済み写真**
- メッセージ: **この写真は削除されているようです。写真ライブラリと同期してください。**
  **同期にはインターネットに繋がった状態で行ってください。**
- ボタン: **ライブラリを再読み込み**

「ライブラリを再読み込み」を押すと §4.4 のブロッキングダイアログへ遷移し、
**完了後に裏で開いている写真プレビューを自動で閉じる**（削除済みの写真を表示し続けない）。

#### 存在するが取得できない場合

削除ではないため別の案内にする。文言案:

- タイトル: **写真を表示できません**
- メッセージ: **この写真の本体が端末にありません。iCloud からダウンロードするには、インターネットに繋がった状態でしばらく待ってから再度お試しください。**

こちらに「ライブラリを再読み込み」ボタンは置かない（再読み込みでは解決しないため）。

### 4.6 設定「地図に表示する写真」

設定画面へドロップダウンを追加する。

- すべて（**既定**）
- 最新200件
- 最新1000件
- 最新3000件
- 最新10000件

説明文:

> ジオタグ付き写真が多いと地図が重くなることがあります。地図に表示する枚数を新しい順で制限できます。

**基準は「全体の最新N件」**（表示範囲ごとではない）。ラベルと挙動が一致して分かりやすい。
古い場所へ移動すると何も表示されないという副作用はあるが、設定した本人には理解できる挙動である。

既定を「すべて」にできるのは、§4.7 の安全上限が内部で効くため。

### 4.7 ビューポート検索の安全上限

`getPhotoAssetsInBounds` に `LIMIT` を入れる（PR #162 の申し送り）。
設定が「すべて」でも、一度に JS へ載る件数を内部で抑える。ユーザーからは見えない保険。

`ORDER BY taken_at DESC` は既にあるため、新しい順で上限まで取る形になる。

### 4.8 サムネイル解決をマーカー単位に絞る

現在は「ビューポート検索の結果全件」を解決している。地図に見えるのは**クラスタの代表1枚**だけなので、
解決回数を**画面上のマーカー数**に比例させる。

- 解決の順序を「検索 → 解決 → クラスタリング」から「検索 → クラスタリング → 代表写真だけ解決」へ変える
- クラスタを開いたとき、そのクラスタの写真を解決する

これにより、ライブラリが何万枚あっても表示コストがほぼ一定になる。
現状（ジオタグ1,400件）では体感できないが、全写真にジオタグを付けるユーザーでは効いてくる。

## 6. テスト方針

- **純粋関数**: 表示上限の解決、差分スキャンの基準時刻の算出、走査モードの判定
- **リポジトリ**: 表示上限つきビューポート検索、`LIMIT` の適用
- **走査**: 差分スキャンが基準時刻より新しいものだけを対象にすること。全件スキャンが上限なしで走ること
- **フック**: キャッシュ先読み（走査完了前に写真が表示されること）、走査完了後の更新
- **UI**: ブロッキングダイアログが操作を遮ること、完了後にプレビューが閉じること、
  削除済み / 取得不可でダイアログが出し分けられること
- **テストできない部分**: `PHAsset` の実挙動、実機での所要時間。実機確認手順を残す

## 7. リスク

| リスク                                         | 対応                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------- |
| 差分スキャンが古い写真の削除・追加を取りこぼす | §4.5 の導線と設定画面の再読み込みで回収する。仕様として文書化する      |
| 存在確認の誤判定でユーザーに誤情報を出す       | 削除と取得不可を明確に分ける。断定的な文言は削除が確認できた場合のみ   |
| 表示上限「すべて」で広域表示が重くなる         | §4.7 の内部上限と §4.8 の解決回数削減で守る                            |
| ブロッキング中にアプリが落ちる                 | 走査結果は完了時にまとめて保存するため、途中終了しても不整合は残らない |

## 8. 非目的

- Android のサムネイル対応（issue #76）
- GPSログとの時刻連動（`docs/photo-geotag.md` §7）
- 写真編集（位置・日時の変更）の追従
- 走査の同時実行数の調整（実測では位置取得が支配的だが、まずは現状維持）

## 9. 承認が必要な点

1. **差分スキャンを自動、全件スキャンを明示操作のみとすること**
2. **明示的な全件スキャン中はブロッキングダイアログで操作を止めること**（結果的に速く終わるため）
3. **削除済みと取得不可を存在確認で分け、文言を出し分けること**
4. **表示上限の基準を「全体の最新N件」とし、既定を「すべて」とすること**
5. **サムネイル解決をクラスタの代表写真だけに絞ること**（解決順序の変更を伴う）
6. §4.5 / §4.6 の**文言**
