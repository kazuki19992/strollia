# 写真ジオタグ表示仕様

## 1. 基本方針

Strollia は任意機能として、写真ライブラリ内の写真メタデータを読み取り、ジオタグ付き写真をマップ上に表示できるようにする。

この機能は必須機能ではない。実装難易度、OS制約、権限審査、パフォーマンス、プライバシーの観点で難しい場合は、初期リリースから外してよい。

## 2. 目的

GPSログ上に写真を重ねることで、ユーザーが「いつ・どこで・何を見たか」を振り返りやすくする。

移動ルートだけではなく、その場所で撮影した写真が吹き出しのように表示されることで、Strollia の記録体験を豊かにする。

## 3. 対象写真

表示対象は、写真ライブラリ内のジオタグ付き写真のみとする。

以下の写真は表示しない。

- ジオタグが存在しない写真
- 位置情報へのアクセス権限がない写真
- ユーザーがアクセスを許可していない写真
- 動画
- 破損している、またはメタデータを読み取れない写真

**ジオタグはあるが画像を取得できなかった写真は、除外せずプレースホルダ付きのマーカーで表示する。**
iCloud にしか本体が無い写真などが該当する。判断基準は「その場所に写真があるという情報を地図に置けるか」であり、
ジオタグが無ければ置けないので除外し、ジオタグがあれば画像が無くても置ける（§9.5）。

## 4. 権限

写真ライブラリへのアクセス権限をユーザーに要求する。

ユーザーが許可した場合のみ、写真メタデータの読み取りを行う。

権限は必須ではなく、拒否されてもGPSログ機能は利用できる。

初期実装では、設定画面の「マップ上に写真を表示」を初めてオンにしたタイミングで写真ライブラリ権限を要求する。写真ライブラリはフルアクセスを必要とし、限定アクセスや拒否の場合は写真表示をオンにしない。

**保存済み設定からの復元時も権限を再確認する。** フルアクセスでメタデータを保存したあとにOS設定で「選択した写真」へ変更されると、`photo_assets` には現在アクセスできない写真の行が残っている。権限を確認せずに復元すると、ユーザーがアクセスを取り消した写真が地図に再表示されてしまう（§11「権限が取り消された場合は写真表示を停止する」）。

- 復元時は `MediaLibrary.getPermissionsAsync()` で**参照するだけ**にし、権限ダイアログを出さない（起動直後に突然ダイアログが出るのを避けるため。権限の要求はONにする導線の責務）
- フルアクセスでない場合は写真表示をオフへ戻し、保存済み設定（`showPhotosOnMap` / pending フラグ）もクリアする
- 復元経路では Alert を出さない。ONにする操作で権限が足りない場合の Alert は従来どおり表示する

想定するライブラリは以下である。

- `expo-media-library`
- 必要に応じて `expo-image-picker`

`expo-media-library` では、アセット情報、EXIF、位置情報、限定アクセス状態などを扱える。

## 5. 表示切り替え

写真表示はユーザーがオン/オフを選択できる。

設定例は以下とする。

- 写真をマップに表示する: オン/オフ
- 表示対象期間の写真のみ表示する: オン/オフ
- サムネイルを表示する: オン/オフ

初期状態はオフとする。理由は、写真ライブラリ権限がセンシティブであり、ユーザーの意図を明確にしたいためである。

保存済みの写真表示ONは、アプリ起動直後に即時復元せず、MapView の準備完了後に有効化する。有効化中は一時的な pending 設定を保存し、写真読み込みとマーカー描画が安定したら解除する。次回起動時に pending が残っている場合は、前回の写真表示でクラッシュした可能性があるため写真表示を自動でオフに戻す。

### 5.1 地図に表示する写真（表示上限）

**走査対象と表示対象は別物である。** 走査は常にライブラリ全体を見て `photo_assets` を最新化し、この設定は「そのうち何件を地図に出すか」だけを決める。

| 設定値                                            | 意味                           |
| ------------------------------------------------- | ------------------------------ |
| すべて（**既定**）                                | 上限なし（内部の安全上限のみ） |
| 最新200件 / 最新1000件 / 最新3000件 / 最新10000件 | 全体の最新N件へ絞る            |

**基準は「全体の最新N件」であり、表示範囲ごとのN件ではない。** 設定のラベルと挙動を一致させるためである。古い場所へ移動すると何も表示されないという副作用はあるが、設定した本人には理解できる挙動である。

既定を「すべて」にできるのは、ビューポート検索に内部の安全上限（`PHOTO_VIEWPORT_SAFETY_LIMIT`）が常に効いているためである（§9.2）。

設定は `app_settings` に保存し、UI層（`usePhotoDisplayLimitSetting`）で保持する。地図のパン・ズームのたびに読み直すと表示のたびにSQLiteへの往復が増えるため、解決済みの件数をビューポート検索へ渡す形にしている。

### 5.2 ライブラリを再読み込み

設定画面から全件走査を実行する導線である（§8.2）。差分走査が取りこぼす「古い範囲での削除」「AirDropやインポートで後から入った古い写真」を回収するために使う。

## 6. マップ上の表示

ジオタグ付き写真は、写真のGPS座標に基づいてマップ上に表示する。

表示方法は以下とする。

- 写真位置にマーカーを表示する
- マーカーは小さい四角い吹き出しとして表示する
- 吹き出し内に写真サムネイルを表示する
- 近接する複数写真は1つの吹き出しへまとめ、右下に `+n` の件数バッジを表示する
- 単体写真のマーカーをタップすると写真を全画面で表示する
- 複数写真の吹き出しをタップすると、吹き出し内に写真グリッドを表示する
- グリッド内の写真をタップすると写真を全画面で表示する。10枚以上ある場合は9枚単位のページとして横スワイプで閲覧する

### 6.1 画像を表示できないときの案内（削除済み / 取得不可）

拡大表示で**高解像度を出せなかったとき**、原因を存在確認で切り分けて案内を出し分ける。区別せずに「削除されています」と出すと、オフラインのユーザーへ誤情報を出すことになる。

**判定の起点は「高解像度を取得できたか」であり、「何かが表示できているか」ではない。** 拡大表示は高解像度を取得できない間サムネイルへフォールバックするため、表示中のURIの有無で判定すると、端末未ダウンロードの写真では案内が一切出なくなる（サムネイルがある限り常に表示できてしまうため）。判定は「高解像度が無い」かつ「取得中でない」ときに走らせ、サムネイルの有無は条件に含めない。

| 原因                                            | 判定                                  | 再読み込みで解決するか |
| ----------------------------------------------- | ------------------------------------- | ---------------------- |
| 写真ライブラリから削除された                    | `isPhotoAssetAvailableAsync` が false | する                   |
| iCloud にあり端末未ダウンロード（オフライン等） | `isPhotoAssetAvailableAsync` が true  | **しない**             |

存在確認は `PHAsset.fetchAssets(withLocalIdentifiers:)` の結果が空かどうかを見るだけで、画像のI/Oもデコードも行わない。

**判定できない場合は必ず「取得不可」へ倒す。** ネイティブモジュールを解決できない環境（Expo Go・jest・Android・旧ビルド）や呼び出しが失敗した場合に「削除された」と誤判定するより、断定を避けるほうが安全である。断定的な文言は削除が確認できた場合だけに使う。

| 状態     | 出し方                       | 「ライブラリを再読み込み」ボタン |
| -------- | ---------------------------- | -------------------------------- |
| 削除済み | **モーダル**（削除済み写真） | **置く**                         |
| 取得不可 | **拡大表示の中へインライン** | **置かない**（解決しないため）   |

**取得不可をモーダルにしないのは、未ダウンロードの写真を開くたびに操作を止められると邪魔になるためである。** サムネイルは表示できているので「写真を表示できません」とも言わない。案内は画像の下へ流し込み（画像の高さを譲る）、写真の上に重ねない。閉じるボタンは置かず、写真を閉じれば消える。

削除済みの案内から「ライブラリを再読み込み」を押すと全件走査（§8.2）へ進み、**完了後に裏で開いている写真プレビューを自動で閉じる**。削除された写真を表示し続けないためである。

なお、サムネイルの見え方は状況で変わる。同一セッション中に削除された写真はメモリキャッシュと書き出し済みファイルが残るためサムネイルが出続け、アプリ再起動後は再解決に失敗して画像なしのプレースホルダになる。どちらでもマーカーは地図に残るため、**拡大表示しようとした時点**で気づける。全件走査の完了時には表示用URIのメモリキャッシュも捨て、削除済み写真の古いサムネイルが残らないようにする。

文言は `src/ui/appText.ts` に集約し、削除済みのモーダルは `src/ui/components/PhotoDeletedDialog.tsx`、取得不可のインライン案内は `src/ui/components/PhotoPreviewModals.tsx`、判定は `src/ui/hooks/usePhotoUnavailableReason.ts`（高解像度の可否は `src/ui/hooks/usePhotoPreviewUri.ts` の `hasHighResolutionPreview`）が受け持つ。

## 7. GPSログとの時刻連動

写真メタデータに撮影日時が含まれる場合、GPSログの時刻と照合する。

日別表示やfrom-to表示では、表示中のGPSログ期間に撮影された写真のみを表示できるようにする。

照合の考え方は以下とする。

- 写真の撮影日時が表示中の範囲内に含まれる場合、表示対象とする
- 写真の撮影日時とGPSログポイントの時刻が近い場合、ルート上の関連写真として扱える
- 写真にジオタグがある場合は、写真自身の位置情報を優先する
- 写真にジオタグがない場合は表示しない

「GPSの時刻と同じもの」の厳密な扱いは、完全一致ではなく、一定の許容範囲を持つ近似一致を検討する。

例:

- 写真撮影時刻の前後1分以内にGPSログがある
- 最も近いGPSログポイントと写真を関連付ける
- ただし、ジオタグなし写真は推定配置しない

## 8. ローカル保存方針

ジオタグ付き写真の**メタデータのみ**を端末内SQLiteへ保存する。写真本体は複製せず、外部送信も一切行わない。

保存するのは以下である。

- 写真アセットID
- 緯度・経度
- 撮影日時
- 表示用URI
- ピクセル寸法
- 最終読み取り日時

写真本体を複製しないことで、ストレージ消費とプライバシーリスクを抑える。

保存する理由は、写真ライブラリの走査が起動のたびに走らせるには重いためである。保存済みメタデータがあれば、**走査の完了を待たずに地図へ写真を出せる**（§8.1）。走査に使うAPIは §9.9 を参照する。

> **かつての記述の誤り**: 以前この節には「2回目以降の起動では走査なしで地図に写真を出せる」とあったが、実装がそうなっていなかった。走査の実行済みフラグが React の ref に置かれていて再起動で消え、しかもDBキャッシュの有無を見ていなかったため、**起動のたびに全件走査が走っていた**。さらにビューポート検索が走査の完了を待っていたため、実機（写真18,218枚）では起動後20秒以上なにも表示されない状態だった。Phase 2-c で §8.1 / §8.2 の形へ直した。

保存したメタデータは全データ削除（`deleteAllUserData`）の対象であり、`photo_assets` も確実に削除される。

保存済みの行は走査のたびに「走査済みの時間窓」と突き合わせ、写真ライブラリから削除された写真やジオタグを失った写真の行を掃除する（§9.3）。

### 8.1 キャッシュ先読み（走査を待たずに表示する）

写真表示の有効化時とアプリ起動時は、**走査の完了を待たずに `photo_assets` から表示する**。

```text
ビューポート検索（photo_assets）→ 即表示
  ↓ 並行して
差分走査 → 完了したらキャッシュを引き直して表示を更新
```

これにより、走査に何秒かかるかがユーザーから見えなくなる。走査中であることは、読み込み帯とは別の控えめな案内（「写真ライブラリの新しい写真を確認しています...」）で示すだけにする。

走査に失敗しても、すでに表示できている写真は消さない。消してしまうと「走査に失敗したせいで地図から写真が消える」という、キャッシュ先読みで避けたかった状態に戻るためである。

実装は `src/ui/hooks/usePhotoMapOverlay.ts`。

### 8.2 走査モデル（差分と全件）

走査には2つのモードがあり、**走る契機と削除検知の範囲が異なる**。

| モード   | 対象                                       | 契機                                         | 削除を検知できる範囲   |
| -------- | ------------------------------------------ | -------------------------------------------- | ---------------------- |
| **差分** | 前回の基準時刻より新しい写真だけ           | 自動（アプリ起動時・写真表示をONにしたとき） | 走査した新しい範囲だけ |
| **全件** | ライブラリ全体（**件数の上限を掛けない**） | ユーザーの明示操作のみ                       | ライブラリ全体         |

**かつてあった「最新200件」の走査上限は撤廃した。** 実測（`docs/superpowers/specs/2026-08-29-photo-scan-limit-removal-design.md` §2）で全ライブラリ走査が24秒と分かり、上限を掛ける根拠が消えたためである。

差分走査の基準時刻（前回の走査で確認できた最新の撮影日時）は `app_settings` に保存する（`src/features/photos/photoScanState.ts`）。基準時刻が無い初回は全件走査へフォールバックする。

**差分走査は「ライブラリを見切った」扱いにしない。** 基準時刻より古い範囲は見ていないため、全期間で突き合わせると保存済みの古い写真の行をすべて削除してしまう。次ページが残っている場合と同じ扱いにし、突き合わせ対象を走査したページの範囲へ閉じる（§9.3）。

全件走査の契機は2つだけである。

- 設定画面の「ライブラリを再読み込み」（§5.1）
- 削除済み写真の案内ダイアログの「ライブラリを再読み込み」（§6.1）

**全件走査の実行中はダイアログで他の操作を止める。** 走査中に地図をパン・ズームすると、ビューポート検索とサムネイル解決が位置情報取得と同じネイティブリソースを取り合い、実測で1.6倍遅くなる。操作させないことで結果的に早く終わる。ダイアログは `exeForMetadata()` が終わって総数が確定するまで不定形の進捗を出し、確定後は「N件中M件」を表示する。

実装は `src/ui/hooks/usePhotoLibrarySync.ts` と `src/ui/components/PhotoLibrarySyncDialog.tsx`。

## 9. データベース

### 9.1 `photo_assets`

| カラム         | 型        | 説明                                                        |
| -------------- | --------- | ----------------------------------------------------------- |
| `asset_id`     | TEXT      | 主キー。写真ライブラリ上のアセットID（`uri` と同値）        |
| `latitude`     | REAL      | 緯度                                                        |
| `longitude`    | REAL      | 経度                                                        |
| `taken_at`     | TEXT NULL | 撮影日時。取得できないアセットがあるためNULL可              |
| `uri`          | TEXT      | 安定した識別用URI（iOS: `ph://…` / Android: `content://…`） |
| `width`        | INTEGER   | 写真の横幅                                                  |
| `height`       | INTEGER   | 写真の高さ                                                  |
| `last_seen_at` | TEXT      | 最終確認日時                                                |
| `created_at`   | TEXT      | 作成日時                                                    |
| `updated_at`   | TEXT      | 更新日時                                                    |

ジオタグがない写真はこのテーブルに保存しない。

**表示用の一時パス（旧APIの `localUri`）は保存しない。** 一時パスはアプリ再起動をまたいで有効である保証がないため。代わりに走査で得た安定URI（新APIの `Asset.id`。iOS: `ph://<localIdentifier>`）を保存する。`asset_id` と `uri` はこの同じ値であり、識別子としても表示用URIの解決元としても安定している。ただし**保存した `uri` はそのままでは `<Image>` で描画できない**。表示に使うURIの解決方法は §9.5 を参照する。

`taken_at` とそのインデックスは §7 のGPSログ時刻連動に向けた準備工事であり、現時点では絞り込みに使わない。

### 9.2 マップ表示範囲での絞り込み

地図に描画する写真は、表示範囲の緯度経度で `photo_assets` を絞り込んでから取り出す。

- 検索範囲は表示範囲の外側へ余白を持たせ（Visited Grid の `boundsPaddingRatio` と同じ考え方）、小さなパンで再取得が走らないようにする
- 余白の内側に表示範囲が収まっている間は再検索しない
- 経度180度線をまたぐ範囲では `BETWEEN` が空集合を返すため、OR条件へ分岐する

絞り込みには2種類の上限が掛かる。役割が異なるので混同しないこと。

| 上限                                          | 出どころ             | 掛かり方                                                              |
| --------------------------------------------- | -------------------- | --------------------------------------------------------------------- |
| **表示上限**                                  | ユーザー設定（§5.1） | 先に全体を `ORDER BY taken_at DESC` でN件へ絞り、そのうち範囲内を返す |
| **安全上限**（`PHOTO_VIEWPORT_SAFETY_LIMIT`） | 内部固定             | 設定が「すべて」でも常に掛かる。ユーザーからは見えない保険            |

表示上限を範囲で絞る**前**に掛けるのは、後に掛けると「表示範囲ごとの最新N件」になり設定の意味が変わってしまうためである。`taken_at` は `new Date(ms).toISOString()` 由来のUTC固定長表記なので辞書順＝時刻順であり、撮影日時が不明（NULL）の行は `DESC` で末尾に来る。最新N件の絞り込みに紛れ込むことはない。

詳細な設計は `docs/superpowers/specs/2026-08-10-photo-map-scan-limit-removal-design.md` と `docs/superpowers/specs/2026-08-29-photo-scan-limit-removal-design.md` を参照する。

### 9.3 走査済みの時間窓との突き合わせ（削除された写真の掃除）

`photo_assets` の行はセッションをまたいで残るため、写真ライブラリ側で削除された写真の行も残り続ける。その行は画像の読み込みに失敗し、地図上に**空のバブル**として表示されてしまう。これを防ぐため、走査のたびに「今回確認できた範囲」に限って保存済みの行と突き合わせ、確認できなかった行を削除する。

走査は撮影日時の降順（新しい→古い）で進む。したがって1ページ走査し終えた時点で、**そのページ内で最も古い撮影日時以降は全部見た**と言える。この範囲を「走査済みの時間窓」と呼び、突き合わせの対象にする。

窓の下限は、走査した**ページ内の全アセット**（ジオタグの有無を問わない）の撮影日時の最小値とする。ジオタグ付きだけで計算すると、実際に見た範囲より窓が狭くなる。

**下限は排他として扱う**（`taken_at > 下限` のみを対象にし、境界時刻ちょうどの行は残す）。撮影日時は一意なカーソルではなく、バースト撮影などで同一時刻の写真が複数枚あると、それがページ境界をまたぎうる。両端閉区間（`>=`）にすると、次ページ側にある**実在するが未走査の写真**が「確認できなかった行」と判定されて削除され、走査上限の外にあるため後の走査でも復活しない。「削除された写真が境界時刻ぶんだけ残りうる」ことを受け入れる代わりに「実在する写真を消さない」を選ぶ、意図的な安全側の判断である。

判定は**安全側に倒す**。削除は破壊的な操作であり、位置情報の取得が一部失敗しただけの走査で実在する写真の行を消してはいけないためである。「残す対象」を先に決め、窓の中でそれ以外を削除する形にしている。

| 状況                                         | 判定                                             |
| -------------------------------------------- | ------------------------------------------------ |
| 今回の走査で再保存された（ジオタグあり）     | **残す**                                         |
| `getLocation()` が成功し、ジオタグが無かった | **削除**（ジオタグを失った）                     |
| `getLocation()` が reject した               | **残す**（存在するがジオタグ不明＝判断不能）     |
| 走査結果にそもそも現れなかった               | **削除**（窓の中は全部見たはずなので消えている） |

窓の端の扱いは以下とする。「さらに古いページが残っているか」の判定方法は §9.9 を参照する。

- さらに古いページが残っている場合は `taken_at > 下限` の行だけを対象にし、**撮影日時が不明（NULL）の行は対象外**にする（窓の内外を判定できないため残す）
- ライブラリ全体を見終わった場合は窓が全期間になるため、`taken_at` が NULL の行も対象にする
- ページ内アセットの撮影日時が全て取れず下限を計算できない場合は、**突き合わせ自体を行わない**
- ページが空でライブラリ末尾でもある場合は「ライブラリが空」を意味するため、保存済みの行はすべて削除される

保存（UPSERT）と削除は同一トランザクションで行い、途中で失敗して中途半端な状態が残らないようにする。突き合わせの失敗は保存の失敗と同じ扱いで、写真表示そのものは継続する。

**写真ライブラリへのフルアクセスが無いときは、突き合わせを行わない**（保存は従来どおり行う）。限定アクセスの走査は「ユーザーが選択した写真」だけを返し、しかも上限に満たない件数で返るため「ライブラリを見切った」ように見える。その結果をそのまま突き合わせると窓が全期間になり、選択されていない写真の行がすべて削除されてしまう。限定アクセスでは**未選択の写真がライブラリに実在するのか削除されたのかを区別できない**以上、`getLocation()` が reject したアセットの行を残すのと同じく「判断できないものは消さない」に倒す。

- 権限は `getPermissionsAsync()` で**参照するだけ**にし、この経路で権限ダイアログを出さない（権限の要求は写真表示を ON にする導線の責務）
- フルアクセスかどうかの判定には `hasFullPhotoAccess` を使う（限定アクセス・拒否のいずれも突き合わせを行わない）
- 権限の参照自体に失敗した場合も、フルアクセスと言い切れないため突き合わせを行わない（安全側）

判定ロジックは `src/features/photos/photoScanWindow.ts` の純粋関数（`resolveScannedWindowOldestTakenAt` / `resolveRetainedAssetIds` / `createPhotoAssetReconciliation`）に切り出してあり、DB操作は `photoAssetRepository.savePhotoAssets` が受け持つ。

> **設計書との差分**: 親設計書（`docs/superpowers/specs/2026-08-10-photo-map-scan-limit-removal-design.md` §4.2）は「削除検知はライブラリ全体の再走査を意味するため Phase 2 のスコープ外」としていた。しかし**走査済みの時間窓に限れば、追加の走査なしで正しく判定できる**。空のバブルが地図に残る実害もあるため、Phase 2-b の走査（最新200件）の範囲で導入した。窓の外（未走査の古い写真）の削除検知は引き続きスコープ外である。

### 9.4 検知できない変化

以下は自動の走査（差分）では検知しない。**設定画面の「ライブラリを再読み込み」による全件走査で回収する**（§5.2 / §8.2）。

- 走査済み窓の**外**で削除された写真（未走査の範囲は突き合わせできない）。差分走査では基準時刻より古い範囲が常にこれに当たる
- AirDropやインポートで**後から入った古い写真**（撮影日時が基準時刻より古いため差分走査の対象にならない）
- 窓の下限と**同じ撮影日時**で削除された写真（下限を排他にしているため境界時刻の行は残る）
- フルアクセスが無い状態で削除された写真（限定アクセスでは未選択写真の存否を判断できないため突き合わせ自体を行わない）
- 走査後にジオタグが付与された写真（窓の内側は再走査しないため）
- 撮影位置・撮影日時が写真アプリ側で編集された場合の追従

### 9.5 表示用URIは保存せず、サムネイルとして都度取得する

**保存した `uri` をそのまま `<Image>` へ渡しても描画できない。** iOS の `ph://<localIdentifier>` を描画するには `RCTPhotoLibraryImageLoader` が必要だが、**React Native 0.86 にこのローダーは存在しない**（`RCTImageLoader.mm` のコメント内で名前が言及されているだけ）。実機では「マーカーは正しい位置に出てクラスタ数も正しいのに、画像だけが白紙」という形で現れる。

したがって表示用URIは、**描画へ回る直前に都度解決する**。キャッシュ保存に失敗して走査結果をそのまま描画するフォールバック経路（§9.6 の `isCacheSaved` が false のとき）でも同じ解決を通し、**`ph://` が `<Image>` へ到達しうる経路を残さない**。

**解決するのは「地図に実際に画像として出る写真」だけである。** かつてはビューポート検索の結果を全件解決していたが、地図に見えるのはクラスタの代表1枚だけなので、`+187` のクラスタでは188枚ぶん書き出して大半が無駄になっていた。そこで解決の順序を組み替えている。

```text
かつて: 検索 → 全件解決 → クラスタリング
現在:   検索 → クラスタリング → 代表写真だけ解決
```

解決対象は次の3つに限る。いずれも「今まさに画像として出す写真」である。

- クラスタの代表写真（地図上のマーカー）
- ユーザーが開いたクラスタの写真（吹き出しのグリッド）
- 拡大表示中の写真

これによりライブラリが何万枚あっても表示コストがほぼ一定になる。

`MapPhoto` は解決前の状態を `uri: null` で表し、解決元の安定URIは `storedUri` に持つ。`uri` が null の写真はプレースホルダで描かれる（§9.6）ので、解決が届くまでの見た目は「画像を取得できない写真」と同じ扱いで済む。`storedUri` を `id` と別に持つのは、PR #167 より前に保存された行では `asset_id` が `localIdentifier`、`uri` が `ph://<localIdentifier>` と食い違うためである。

実装は `src/features/photos/photoDisplayUri.ts`（`resolvePhotoDisplayUriMap` / `applyResolvedPhotoUris`）と `src/ui/hooks/usePhotoDisplayUris.ts`。

| 値                                              | どこに置くか    | 理由                                                                 |
| ----------------------------------------------- | --------------- | -------------------------------------------------------------------- |
| `ph://<localIdentifier>`                        | SQLite（`uri`） | 再起動をまたいで安定した識別子。DBに持つべき値                       |
| 解決後の `file://…`（キャッシュ上のサムネイル） | メモリのみ      | キャッシュディレクトリは OS が消しうる。永続化すると次回起動で白紙化 |

#### なぜ `PHImageManager` なのか

利用できる API はどれも**オリジナル本体**を要求し、かつネットワークアクセスを行わない。
設定 → 写真 → **「iPhone のストレージを最適化」**が有効な端末ではオリジナルが iCloud へ退避されるため、
これらは軒並み nil を返し、地図上の写真が1枚も出なくなる。

| 経路                                 | 実際の挙動                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 旧 `getAssetInfoAsync`               | `requestContentEditingInput` の `fullSizeImageURL`。App Hang 対策で `shouldDownloadFromNetwork: false` |
| 新 `Asset.getUri()`                  | `UriExtractor` が `PHContentEditingInputRequestOptions()` の既定値（ネットワーク不許可）で要求         |
| `expo-file-system` の `ph://` コピー | `PHAssetResourceManager.writeData` を `options: nil` で呼ぶ。同じ制約                                  |

写真アプリが一覧を出せるのは **`PHImageManager.requestImage`** を使っているためで、これはオリジナルが端末に
無くてもローカルのサムネイルを返す。この API を公開しているパッケージが無いため、**iOS 専用のローカル
Expo モジュール `modules/photo-thumbnail/` を自前で追加している**（設計書
`docs/superpowers/specs/2026-08-23-photo-thumbnail-module-design.md`）。

- 公開APIは `getPhotoThumbnailAsync(assetId, size)` の1つだけ。取得できない場合は例外を投げず `null` を返す
- `PHImageRequestOptions.isNetworkAccessAllowed = false` — **iCloud からのダウンロードは行わない**。
  true にすると通信・待ち時間・App Hang のリスクをすべて負い直すことになるため、この設定は変更しない
- `deliveryMode` は結果ハンドラが1回だけ呼ばれる設定にする（`.opportunistic` は複数回呼ばれ Promise の二重解決になる）
- 取得した画像は JPEG としてキャッシュディレクトリへ書き出す。ファイル名は `assetId` と `size` から決定的に導くため、
  同じ要求は書き出し済みファイルをそのまま再利用する
- モジュールの解決には `requireOptionalNativeModule` を使う。Expo Go・テスト環境・万一のビルド不整合で
  モジュールが無くても import 時に落ちず、「取得できなかった」と同じ扱いになる
- **ネイティブモジュールを含むため、この修正は OTA では配れない。ネイティブビルドが必要になる**

Android 実装は持たない。Android の `photo_assets` には `content://` が入っており `<Image>` でそのまま描画できる見込みのため、
JS 側が `ph://` 以外を素通しする（**Android は未リリースのため実機未確認**。issue #76）。
Android のサムネイル API（`ContentResolver.loadThumbnail`）対応も issue #76 のスコープ。

#### 拡大表示のときだけ iCloud からのダウンロードを許可する

マーカー用サムネイル（512px）を拡大表示に流用すると、全画面では画像が粗い。そこで**拡大表示のときだけ**
高解像度の画像を取り直す。モジュールが公開する関数は2つで、**ネットワークアクセスの可否がこの2つを分ける理由**である。

| 関数                     | 用途         | `isNetworkAccessAllowed`   | `deliveryMode`       | 要求サイズ                |
| ------------------------ | ------------ | -------------------------- | -------------------- | ------------------------- |
| `getPhotoThumbnailAsync` | 地図マーカー | **false**（通信しない）    | `.fastFormat`        | 512px 固定                |
| `getPhotoPreviewAsync`   | 拡大表示     | **true**（例外はここだけ） | `.highQualityFormat` | 画面の長辺 × ピクセル密度 |

線引きの理由は以下のとおり。

- **地図描画中に通信を走らせない。** マーカーのサムネイル取得はビューポート内の写真ぶんが一斉に走る。
  ここで通信を許すと、通信量・待ち時間・App Hang という元の問題がそのまま再発する
- **拡大表示はユーザーが写真を明示的にタップしたときにしか走らない。** 1枚ずつで、待たされても意図が伝わる。
  ローカルファースト方針（ユーザーの明示操作なしに通信しない）とも矛盾しない
- 要求サイズを画面の長辺ピクセル数にするのは、**画面が表示できる以上のピクセルを要求しないため**。
  端末の向きで値が変わらないよう長辺基準にする（要求サイズは書き出しファイル名に入るため、
  値が揺れると同じ写真を何度も書き出し直すことになる）
- `deliveryMode` は `.highQualityFormat`。ダウンロードを待ってでも最終品質の画像を**1回だけ**受け取る
  （結果ハンドラの二重呼び出し対策は `.fastFormat` と同じく保険として残す）

UI 側（`usePhotoPreviewUri` → `PhotoPreviewModals`）の振る舞い。

- 拡大表示を開いた瞬間は**すでに手元にあるサムネイルを表示する**（取得を待たせない）
- 裏で高解像度を取得し、取得できたら差し替える。取得中はローディングインジケータを出す
- **取得できなかった場合（機内モード・オフライン等）はサムネイルのままにする。** エラー表示や黒画面にしない
- 別の写真へ切り替えたあとに前の写真の結果が遅れて届いても反映しない

#### JS 側の実装（`src/features/photos/photoDisplayUri.ts` と `photoLibrary.ts` の `loadGeotaggedPhotosInBounds`）

- 解決結果は**セッション内のメモリキャッシュ**（`Map<assetId, 表示用URI>`）に載せる。キャッシュディレクトリは OS が
  消しうるのでSQLiteへ保存してはいけない（保存すると次回起動時に存在しないパスを渡して再び白紙になる）。
  地図のパン・ズームで検索が走っても、同じ写真の解決は1回で済む
- 解決は `mapWithConcurrency` で `PHOTO_INFO_CONCURRENCY` 件までに絞る。フル解像度デコードは伴わないが
  サムネイルのデコードとJPEGの書き出しは走るため、一斉並列にする理由がない
- **サムネイルを取得できなかった写真も結果から除外せず、`uri: null` のまま返す**（§9.6）
- `ph://` 以外のURI（Androidの `file://`）は `<Image>` でそのまま描画できるため、ネイティブへ問い合わせず素通しする
- 失敗はキャッシュしないので、次回の読み込みで再試行される
- **走査経路のフォールバック（`isCacheSaved` が false のとき走査結果を直接表示する経路）でも `ph://` を表示に使わない。** 新APIへの移行後、`toMapPhoto` は `Asset.id`（iOS では `ph://…`）をそのまま `uri` に入れる。そのためフォールバック経路でも `resolveMapPhotoDisplayUris` を通して表示用URIへ解決し、解決できなければ `uri: null`（プレースホルダ表示）とする。`ph://` が `<Image>` へ到達しうる経路は残さない（§9.5）。DBへ保存する `uri` は従来どおり `ph://` のまま（§9.1）

### 9.6 画像を取得できなかった写真はプレースホルダで表示する（除外しない）

かつては解決に失敗した写真を**結果から除外**していた。空のバブルが地図に残るのを避けるためだったが、
「iPhone のストレージを最適化」が有効な端末では解決が**全件失敗**するため、地図から写真マーカーが
丸ごと消えるという、より悪い症状になった。

したがって現在は**除外せず、画像なしのマーカーとして表示する**。

- 写真がそこに存在するという情報自体に地図上の価値がある
- 全件取得できない環境でも、地図が「何も無い」状態にはならない
- `MapPhoto.uri` の型は `string | null`。nullは「ジオタグはあるが画像を用意できなかった」を意味する

描画側は以下のとおり（いずれも白紙・黒画面にしない）。

| 箇所               | 画像がない場合の表示                                             |
| ------------------ | ---------------------------------------------------------------- |
| 地図マーカー       | 吹き出し内に写真アイコンのプレースホルダ。件数バッジは従来どおり |
| クラスタの写真一覧 | マスをプレースホルダにし、タップして拡大表示へは進める           |
| 拡大表示           | アイコンと「この写真の画像を表示できません」を表示               |

読み上げ文言も画像の有無で切り替える（`写真n枚を開く` / `写真n枚を開く（画像を表示できません）`）。

なお**「ジオタグが無い写真は除外」という扱いは変えていない**（§3）。除外をやめたのは
「ジオタグはあるが画像を取得できなかった」写真だけである。

### 9.7 実機での確認手順

`PHImageManager` の実挙動は jest でテストできない。以下は実機で確認する。

1. 設定 → 写真 → **「iPhone のストレージを最適化」**が有効な端末で確認する
2. 地図上の写真マーカーにサムネイルが表示されること
3. **機内モードでもサムネイルが表示されること**（ネットワークアクセスしていないことの確認）
4. アプリを再起動しても表示されること
5. 地図をパン・ズームしてもサムネイル取得が繰り返し走らないこと（メモリキャッシュと書き出し済みファイルの再利用）
6. ローカルのサムネイルすら無い写真があった場合、マーカーが消えずプレースホルダで表示されること
7. 写真をタップした拡大表示で、**サムネイルが即座に出たあと高解像度へ差し替わること**（取得中はインジケータが出る）
8. **機内モードでの拡大表示は、サムネイルのまま据え置かれること**（黒画面やエラーにならない）

Phase 2-c（走査上限の撤廃・同期モデルの見直し）では、次も実機で確認する。

1. **起動直後にキャッシュから写真が出ること**（走査の完了を待たないこと）
2. **200件を超える写真が地図に出ること**（走査上限の撤廃）
3. 設定「地図に表示する写真」の上限が効くこと（例: 最新200件にすると古い場所で表示が消える）
4. 「ライブラリを再読み込み」でブロッキングダイアログが出て、総数確定後に「N件中M件」へ変わり、完了後に地図の表示が更新されること
5. 削除済み写真を開くと削除済みの案内が出て、「ライブラリを再読み込み」後にプレビューが自動で閉じること
6. **機内モードで未ダウンロードの写真を開くと、サムネイルが出ていてもモーダルではなくインラインの案内が出ること**（サムネイルがあるだけで案内が抑止されないこと・削除済みと誤案内しないことの確認）
7. 計測フラグで所要時間を再測定し、2回目以降の起動で差分走査が軽いことを確認すること

### 9.8 クラスタ半径の基準（ビューポート高さの約1割）

写真マーカーをまとめる半径は、表示範囲（`latitudeDelta`）から段階的に決める（`src/features/photos/photoClusters.ts`）。

**基準は「その段階の表示範囲の高さの約1割」である。** 緯度1度は約111kmなので、
段階の上限 `latitudeDelta` と `radiusMeters` の比はおよそ 1:10000 になる（0.003 → 30m、4.5 → 45,000m）。

| 段階の上限 latitudeDelta | 表示範囲の高さ | クラスタ半径 |
| ------------------------ | -------------- | ------------ |
| 0.003                    | 約 333m        | 30m          |
| 0.045                    | 約 5.0km       | 450m         |
| 0.45                     | 約 50km        | 4,500m       |
| 4.5                      | 約 500km       | 45,000m      |
| 4.5 以上                 | —              | 50,000m 固定 |

この比率を選ぶ理由は、**マーカーの視覚サイズと基準を揃えるため**である。
地図上の写真マーカーは画面上で60〜70px、画面高さ700pxに対して**約10%**を占める。
かつて半径は表示範囲の約3%しかなく、「見た目には完全に重なっているのにまとまらない。
もっと縮小するとようやくまとまる」という挙動になっていた。半径を視覚サイズと同じ約10%へ揃えることで、
**「マーカーが視覚的に重なるなら、まとまる」**という一貫した基準になる。

- 半径ではなく段階の境界（`maxLatitudeDelta`）を1/3にする選び方もあるが、その場合フォールバック（50,000m）へ
  移る `latitudeDelta` まで1/3になり、最終段階からフォールバックへの飛びが 15,000m → 50,000m と大きくなる。
  半径側を3倍にすれば最終段階は45,000mとなり、50,000mへ滑らかに繋がる
- **最大段階は 50,000m を超えてはいけない。** 50,000m は空間ハッシュの3セル探索がO(N²)参照実装と
  等価であることを確認できている上限であり（緯度70度程度まで検証済み。200,000mでは崩れる）、
  フォールバック値との関係が壊れる
- 段階境界のちらつきは従来どおりヒステリシス（比率0.2）で抑える

### 9.9 写真ライブラリの走査に使うAPI（expo-media-library 新API）

走査は SDK 57 のクラスベース新API（`Query` / `Asset`）で行う（`src/features/photos/photoLibrary.ts` の `loadGeotaggedPhotos`）。旧 `expo-media-library/legacy` は参照していない。

```text
new Query()
  .eq(AssetField.MEDIA_TYPE, MediaType.IMAGE)
  .orderBy({ key: AssetField.CREATION_TIME, ascending: false })
  .limit(上限 + 1)
  .exeForMetadata()                       → 1回（id/撮影日時/寸法をまとめて取得）
  → 各 id について new Asset(id).getLocation()  → N回
```

**`uri` は `AssetMetadata.id`（iOS: `ph://<localIdentifier>`）をそのまま使う。**
`Asset.getUri()` は `requestContentEditingInput` を伴い、iCloud にしか本体が無い写真では失敗する。`id` は I/O 無しで得られるうえ `photo_assets.uri` に保存する値と同一なので、走査では `getUri()` を**使ってはいけない**。

**移行時に `photo_assets` を一度だけ空にする。** `asset_id` に入る値の形が旧APIから変わったため、旧形式の行を残すと同じ写真が新旧2行として共存し、地図に重複マーカーが出る。`photo_assets` は再走査で作り直せるキャッシュなので、`initializeDatabase()` で一度だけ全行を削除する（`docs/data-storage.md` §4.8）。

**「さらに古いページが残っているか」は `limit + 1` のプロービングで判定する。** 新APIに `hasNextPage` は無いため、上限より1件多く要求し、

- 返却件数が上限を超える → さらに古い写真が残っている。**保存対象は先頭の上限件数へ切り詰める**（超過分には `getLocation()` を発行しない）
- 上限以下 → ライブラリを見切った

この真偽値をそのまま §9.3 の突き合わせへ渡す。

位置情報だけは `exeForMetadata()` に含まれないため、アセットごとに `getLocation()` が必要である。往復回数は旧APIと同じだが、`getLocation()` は `phAsset.location` を直接読み取るだけでフル解像度デコードも I/O も伴わないため、1回あたりのコストは桁違いに安い。

**新旧で `PHFetchOptions` の設定が異なる。** 旧 `getAllAssets()` は `includeAssetSourceTypes = .typeUserLibrary` を指定していたが、新 `Query` は指定しない（`Query` に相当するフィルタが無い）。iTunes 同期アセットや共有アルバムの写真まで対象に入り、**新APIの方が多く返す可能性がある**。共有アルバムの写真は `getLocation()` や表示用URIの解決に失敗しうるが、取得できない写真はプレースホルダ表示になるため壊れはしない（§9.5・§3）。

#### 移行後に実機で確認すること

1. 写真マーカーが従来どおり表示される
2. **走査件数が想定外に増えていない**（上記 `PHFetchOptions` の差の確認。`load` ステージの `scannedAssetCount` / `geotaggedPhotoCount` で見る）
3. 走査の所要時間を記録する（`load` ステージの `durationMs`。走査上限の撤廃を検討する際の実測値にする）

## 10. パフォーマンス方針

写真ライブラリ全体を毎回走査すると重くなる可能性があるため、以下を検討する。

- 初回のみ写真ライブラリをスキャンする
- 以後は差分更新する
- 表示中の期間に関係する写真だけ読み込む
- マップ表示範囲内の写真だけ表示する（実装済み。§9.2）
- ズームレベルに応じて近接写真をクラスタリングする。拡大時は狭い範囲、縮小時は広い範囲でまとめる
- サムネイルを遅延読み込みする

### 写真詳細取得の並列数制限

旧APIの `getAssetInfoAsync`(iOS)は、完了コールバック内でフル解像度画像をメインキュー上でデコードしていた。
走査対象(最大200件)へ一斉並列で発行すると、メインスレッドが長時間ブロックされアプリがフリーズする
(2026-08-08 Sentry で App Hang を観測)。

このため `loadGeotaggedPhotos` は位置情報取得の同時実行数を 4 に制限して呼び出す。
**走査上限(200件)は Phase 2-c で撤廃したが、同時実行数の制限は残す。** 上限の撤廃で一度に扱う
件数がむしろ増えるため、一斉並列を避ける必要は変わらないからである(§8.2)。

新APIの `Asset.getLocation()` はデコードを伴わないため、この上限は緩められる余地がある。
ただし**実測してから**変えるべきなので、新API移行では値を据え置いている(§9.9)。

同じ上限(`PHOTO_INFO_CONCURRENCY`)を、§9.5 の表示用URI解決でも共有する。解決はフル解像度デコードを
伴わないが、`PHImageManager.requestImage` はサムネイルのデコードとJPEGの書き出しを行うため、
一斉並列で発行する理由がないため。定数は走査・表示のどちらにも依存しない
`src/features/photos/photoScanConcurrency.ts` に置いている(走査側モジュールに置くと、表示側が
SQLite接続まで引き込んでしまうため)。

### 座標の型がOSで食い違う問題(必ず境界で数値へ変換する)

> **新APIでの状況**: 新APIの `Asset.getLocation()` は iOS / Android とも `Double` を返すため、下記の食い違いは解消している。
> それでも**境界での数値変換は残している**。コストがほぼゼロである一方、「ライブラリの型宣言と実装は食い違いうる」という
> 教訓をテストごと残す価値があるためである(移行設計書 §4.4)。以下は旧APIで実際に起きた事象の記録である。

旧APIの `expo-media-library/legacy` は緯度経度の型定義と実装が一致していなかった。**iOS は文字列、Android は数値**を返す。

| OS      | ネイティブ実装                                                              | 実行時の値  |
| ------- | --------------------------------------------------------------------------- | ----------- |
| iOS     | `ios/MediaLibraryUtilities.swift` の `exportLocation` が `[String: String]` | `"35.6812"` |
| Android | `AssetUtils.kt` が `putDouble` で格納                                       | `35.6812`   |

一方で型定義(`build/legacy/MediaLibrary.d.ts`)は `type Location = { latitude: number; longitude: number }`
であり、`getAssetInfoAsync` の JS 側にも正規化処理は無い。したがって **iOS では型定義に反して文字列が返る**。

この食い違いは静かに壊れる。クラスタリング(`photoClusters.ts`)は乗除算しか使わないため JS の暗黙の
数値変換が効いてしまい、読み込み件数もクラスタ件数も正常に見える。しかし `<Marker coordinate>` へ
文字列が渡った時点で、New Architecture (Fabric) の codegen が `Double` を期待しているため座標を
解決できず、**エラーも例外も出さずにマーカーだけが表示されない**(issue #160、v1.1.3 でも発生)。

対処方針は以下とする。

- `MapPhoto` の型は `number` のまま維持する
- 境界である `toMapPhoto`(`src/features/photos/photoLibrary.ts`)で数値へ変換し、アプリ内部は数値だけを扱う
- 数値として解釈できない値(`NaN` / `Infinity` / `'abc'` / 空文字)の写真は、地図に置けないため除外する
- テストのモックは文字列と数値の両方を通す

この変換は「冗長な型変換」ではなくライブラリ側の型不一致を吸収するためのものなので、削除してはいけない。

### 走査コストの計測フラグ（一時）

走査コストを実機で測るための仕組みである。走査上限（200件）の撤廃（Phase 2-c）はこの計測結果に基づいて設計した（親設計書の「1万枚で約8分」は未実測の試算で、実測とは約40倍の乖離があった）。

**上限の撤廃後も残している。** 差分走査が実際に軽くなっているか、ライブラリが大きい端末で全件走査が何秒かかるかを測り続けるためである。`EXPO_PUBLIC_PHOTO_SCAN_LIMIT` が設定されているときだけ走査に上限が掛かり、未設定なら上限なしで走る（既定の挙動）。

Sentry は production プロファイルでしか送信しない（§12）ため、preview ビルドでは**画面上で数字を読む**。ユーザーが preview ビルドを作り、地図画面のスクリーンショットで結果を報告する運用を想定している。

| 環境変数                             | 役割                                                                                        |
| ------------------------------------ | ------------------------------------------------------------------------------------------- |
| `EXPO_PUBLIC_PHOTO_SCAN_LIMIT`       | 走査に上限を掛ける。**未設定・数値として不正・0以下の場合は上限なし**（既定の挙動）         |
| `EXPO_PUBLIC_LOG_PHOTO_SCAN_METRICS` | `true` のとき、地図画面に走査の計測結果を表示する。無効なときは一切表示しない（既定の挙動） |

計測フラグを有効にすると、写真の読み込み帯（「ジオタグ付き写真を読み込んでいます...」）と同じ場所に次の2行を表示する。差分走査と全件走査のどちらが走ったかは走査結果の `mode` で分かる。

```text
走査 2000件 / ジオタグ 143件 / 失敗 2件
メタデータ 0.3s / 位置 11.8s / 保存 1.2s / 合計 13.3s
```

読み方は以下のとおり。

| 表示       | 内容                                                          |
| ---------- | ------------------------------------------------------------- |
| 走査       | 走査したアセット件数（次ページ判定用の超過分は含まない）      |
| ジオタグ   | ジオタグを持っていた件数                                      |
| 失敗       | `getLocation()` が reject した件数                            |
| メタデータ | `exeForMetadata()` の所要時間                                 |
| 位置       | `getLocation()` 全体の所要時間                                |
| 保存       | `savePhotoAssets`（走査済み窓との突き合わせを含む）の所要時間 |
| 合計       | 走査全体の所要時間                                            |

内訳を分けているのは、「メタデータ取得は件数に対してほぼ一定か」「位置情報取得が支配的か」「DB保存が効いてくるのは何件からか」を見分けるためである。これが分からないと1万件への外挿ができない。

計測そのもの（`Date.now()` の差分）はフラグに関係なく常に行い、フラグは**画面表示だけ**を切り替える。件数を変えて測る手順は次のとおり。

1. `.env.local` に `EXPO_PUBLIC_LOG_PHOTO_SCAN_METRICS=true` と `EXPO_PUBLIC_PHOTO_SCAN_LIMIT=<件数>` を設定する
2. preview ビルドを作成して実機へ配布する（`.claude/skills/build-preview/SKILL.md`）
3. 設定で写真表示をONにし、地図画面に出る計測結果をスクリーンショットで記録する
4. 件数を変えて 1〜3 を繰り返す（200 → 1000 → 2000 …）

上書きが有効なビルドでは、地図画面に「開発フラグ有効」バナーが出る。通常のリリースビルドと取り違えないための表示である。

## 11. プライバシー方針

写真ライブラリには非常にセンシティブな情報が含まれるため、この機能は明示的なユーザー操作で有効化する。

アプリは以下を守る。

- ユーザー許可なしに写真ライブラリへアクセスしない
- ジオタグ付き写真のみを対象にする
- 写真本体をDBに保存しない
- 保存するのはジオタグ付き写真のメタデータのみとし、保存先は端末内SQLiteに限る（§8）
- 写真データを外部サーバーへ送信しない
- 権限が取り消された場合は写真表示を停止する
- 全データ削除で保存済みの写真メタデータも削除する

## 12. 調査用の Sentry 計装

実機(production ビルド)でのみ再現する「設定を ON にしてもマップに写真が表示されない」不具合を
切り分けるため、写真表示パイプラインの各段階に**一時的な**診断計装を入れている。

送信は既存の Sentry 基盤に乗るため、以下が自動的に守られる。

- `isSentryEnabledForBuild()` により production profile のビルドでのみ送信される
- `filterSentryEventBeforeSend` により、不具合レポート設定が OFF のユーザーからは送信されない

送信量は「写真表示 ON」1 回につき最大 3 イベント。ズームやパンでは増えない。

### 12.1 送信する項目

いずれも `investigation_area: photo-map` タグと `photo_map_stage` タグを付けた info メッセージとして
`src/config/sentry.ts` の `reportPhotoMapDiagnostics` から送る。

| ステージ     | 送信箇所                                        | 送信する値                                                                                                                                           |
| ------------ | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `permission` | `src/ui/hooks/usePhotoMapCrashBreaker.ts`       | `granted` / `accessPrivileges` / `hasFullAccess`                                                                                                     |
| `load`       | `src/features/photos/photoLibrary.ts`           | `requestedLimit` / `scannedAssetCount` / `hasNextPage` / `assetInfoFulfilledCount` / `assetInfoRejectedCount` / `geotaggedPhotoCount` / `durationMs` |
| `cluster`    | `src/ui/hooks/usePhotoMapClusterDiagnostics.ts` | `photoCount` / `clusterCount`                                                                                                                        |

`permission` は権限要求を通る経路でのみ送る。保存済み設定からの復元経路は権限要求を通らないため送らない。
`cluster` は写真の読み込みが完了し、かつ写真一覧の参照が前回送信時から変わったときだけ送る。
読み込み前の初期値(空配列)は結果ではないため送らず、`photoCount: 0` の偽イベントが出ないようにしている。
ズームでクラスタ半径のみが変わる場合も送らない。

#### `accessPrivileges` の読み方(OS差分)

`accessPrivileges` は `expo-media-library` の `PermissionResponse` において optional な項目であり、
取りうる値と意味は以下である。

| 値                  | 意味                                                                            |
| ------------------- | ------------------------------------------------------------------------------- |
| `all`               | 写真ライブラリ全体へのアクセスが許可された                                      |
| `limited`           | ユーザーが選択した写真だけアクセスが許可された(限定アクセス)                    |
| `none`              | 拒否された、またはまだ許可されていない                                          |
| 未設定(`undefined`) | OS/実装が `accessPrivileges` を返さなかった。診断イベントでは `null` として送る |

OS差分は以下のとおり。

- iOS: 権限応答から常に設定される。`limited`(選択した写真のみ)が発生しうるのは iOS 14 以降。
- Android: `limited` が発生しうるのは Android 14 (API 34) 以降のみ。API 34 未満では許可なら `all`、それ以外は `none` を返す。

診断イベントの `accessPrivileges: null` は**「拒否」を意味しない**。あくまで「OS が `accessPrivileges` を
返さなかった」であり、`granted` と併せて読む必要がある。`hasFullPhotoAccess`
(`src/features/photos/photoLibrary.ts`)も同じ前提で、`granted` が true かつ `limited` / `none` の
いずれでもない場合をフルアクセスとして扱う。したがって未設定の場合は `granted` の値がそのまま判定結果になる。

### 12.2 送信しない項目

ローカルファースト方針(AGENTS.md §5)に従い、以下は**一切送信しない**。

- 写真の座標(緯度・経度)
- アセットID
- 写真の URI・ファイル名
- 撮影日時
- 写真本体・サムネイル

送るのは件数・真偽値・所要時間・`accessPrivileges` 文字列だけである。

### 12.3 撤去について

これは原因特定のための一時的な計装である。原因が確定して修正が入った後、
`load` / `cluster` ステージの常時送信は撤去するか、閾値付き(件数が 0 のときだけ送る等)へ
絞り込むことを検討する。
