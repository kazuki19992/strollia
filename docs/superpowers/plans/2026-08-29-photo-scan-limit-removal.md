# データ層

## Task 1: アセット存在確認をネイティブへ追加

`modules/photo-thumbnail/` に、写真ライブラリ上にアセットが存在するかを返す関数を追加する。

```ts
/**
 * 写真ライブラリにアセットが存在するかを返す。
 *
 * 画像を取得できない原因が「削除された」のか「iCloudにあり端末に無い」のかを区別するために使う。
 * 区別せずに「削除されています」と案内すると、オフラインのユーザーへ誤情報を出すことになる。
 */
export async function isPhotoAssetAvailableAsync(assetId: string): Promise<boolean>;
```

- iOS 実装は `PHAsset.fetchAssets(withLocalIdentifiers:)` の結果が空かどうかを見るだけ。
  **I/O もデコードも行わない**
- `ph://` 接頭辞の扱いは既存の `getPhotoThumbnailAsync` と揃える
- `requireOptionalNativeModule` を使い、モジュールが無くても落ちないこと。
  解決できない場合は **`true`（存在する）を返す**。存在確認できないときに「削除された」と
  誤判定するより、案内を出さない方が安全なため
- Android 実装は作らない（`ph://` 以外は `true` を返す）

## Task 2: 走査状態の永続化

`src/features/photos/photoScanState.ts` を新設する。

- 前回の走査で確認できた**最新の撮影日時**を `app_settings` へ保存・読み出しする
- 保存キーは既存の命名に合わせる（例: `photoLibraryLastScannedTakenAt`）
- 値が無い（初回）場合を扱えること
- 純粋関数にできる部分（走査結果から次回の基準時刻を求める）は切り出してテストする

**注意**: 撮影日時が不明（NULL）のアセットは基準時刻の算出に使えない。除外して扱うこと。

## Task 3: 走査モード（差分 / 全件）

`src/features/photos/photoLibrary.ts` の走査に**モード**を導入する。

| モード | 対象 | いつ |
| --- | --- | --- |
| 差分 | 前回の基準時刻より新しい写真だけ（`Query.gt(CREATION_TIME, …)`） | 自動（起動時・写真表示ON時） |
| 全件 | ライブラリ全体（**上限なし**） | ユーザーの明示操作のみ |

- **`DEFAULT_PHOTO_SCAN_LIMIT`（200件）の上限を撤廃する。** 全件モードは上限を掛けない
- 計測用の `EXPO_PUBLIC_PHOTO_SCAN_LIMIT` は**残す**（今後の計測に使うため）。
  設定されている場合はそれを上限にする
- `hasNextPage` 相当の判定（`limit + 1` プロービング）は、上限を掛けるときだけ必要。
  上限なしの全件走査は常に「ライブラリを見切った」扱いになる
- **走査済み時間窓の突き合わせ（`photoScanWindow.ts`）は変更しない。**
  差分モードでは窓が新しい範囲だけになり、その範囲の削除だけが検知される（設計どおり）
- 全件走査の完了時に、Task 2 の基準時刻を更新する

**差分モードで基準時刻が無い（初回）場合は全件走査にフォールバックする。**

## Task 4: 表示上限の設定を永続化

`src/features/settings/` に「地図に表示する写真」の上限設定を追加する。

- 値: `all` / `200` / `1000` / `3000` / `10000`（既定 `all`）
- `.claude/skills/add-setting/SKILL.md` の手順に従う
- 純粋関数で「設定値 → SQLの LIMIT 値（`all` なら null）」を解決し、単体テストする

## Task 5: リポジトリの上限対応

`src/features/photos/photoAssetRepository.ts` の `getPhotoAssetsInBounds` に2種類の上限を入れる。

1. **表示上限（ユーザー設定）**: 「全体の最新N件」の中からビューポートで絞る。
   表示範囲ごとではなく**全体**で新しい順にN件である点に注意
2. **安全上限（内部固定）**: 設定が `all` でも一度に JS へ載る件数を抑える。
   ユーザーからは見えない保険

`ORDER BY taken_at DESC` は既にあるため、それを活かす。
日付変更線をまたぐ場合の OR 分岐を壊さないこと。

### テスト

- 表示上限が「全体の最新N件」として効くこと（表示範囲ごとではないこと）
- `all` でも安全上限が効くこと
- 日付変更線をまたぐ既存テストが通ること

# UI層

## Task 6: キャッシュ先読み（最優先）

`src/ui/hooks/usePhotoMapOverlay.ts` を、**走査を待たずに表示する**形へ変える。

現在:

```text
setIsLoadingPhotos(true) → await syncPhotoAssets() → ビューポート検索
```

変更後:

```text
ビューポート検索（キャッシュ）→ 即表示
  ↓ 並行して
差分スキャン → 完了したら表示を更新
```

- 起動直後・写真表示ON直後から、DBにある写真がすぐ出ること
- 走査の完了で表示が更新されること
- 走査中であることは邪魔にならない形で示す（既存の読み込み表示の扱いは調整してよい）

**`assetSyncPromiseRef` が ref のため再起動で毎回フル走査になっていた**のが元の問題。
差分モード（Task 3）になることで、そもそも走査が軽くなる。

## Task 7: サムネイル解決をクラスタの代表写真だけに絞る

現在は「ビューポート検索の結果全件」を解決している。地図に見えるのは代表1枚だけなので、
解決順序を組み替える。

```text
現在: 検索 → 全件解決 → クラスタリング
変更: 検索 → クラスタリング → 代表写真だけ解決
```

- クラスタを開いたときに、そのクラスタの写真を解決する
- `MapPhoto.uri` は解決前 `null`。プレースホルダ表示の既存挙動がそのまま使える
- 解決結果のメモリキャッシュ（`photoDisplayUri.ts`）はそのまま活かす

**これは今回で最も影響範囲が広い変更。** クラスタリングと解決の依存関係が逆転するため、
既存テストが多く壊れる可能性がある。挙動が変わっていないことを丁寧に確認すること。

## Task 8: 明示的な全件スキャン（ブロッキング）

- `src/ui/hooks/usePhotoLibrarySync.ts`（新設）: 全件スキャンの実行・進捗・完了通知
- `src/ui/components/PhotoLibrarySyncDialog.tsx`（新設）: 進捗つきブロッキングダイアログ

要件:

- 実行中は**他の操作をブロックする**（設計書 §4.4。競合を避けて結果的に早く終わらせるため）
- 進捗は `exeForMetadata()` 完了後に総数が分かるので「N件中M件」を表示する。
  それ以前は不定形の表示にする
- 完了したら地図の表示を更新する
- 既存の `IndeterminateProgressBar` / `DeterminateProgressBar` が使えるか確認し、
  使えるなら再利用する（DESIGN.md を参照）

## Task 9: 削除済み / 取得不可のダイアログ

`src/ui/components/PhotoUnavailableDialog.tsx`（新設）。

写真の拡大表示で画像を取得できなかったとき、**Task 1 の存在確認で分岐**して案内を出す。

**削除済み（存在しない）**

- タイトル: `削除済み写真`
- メッセージ: `この写真は削除されているようです。写真ライブラリと同期してください。同期にはインターネットに繋がった状態で行ってください。`
- ボタン: `ライブラリを再読み込み`
- 押すと Task 8 のブロッキングダイアログへ遷移し、**完了後に裏で開いているプレビューを自動で閉じる**

**取得不可（存在するが取れない）**

- **「ライブラリを再読み込み」ボタンは置かない**（再読み込みでは解決しないため）

文言は `src/ui/appText.ts` へ集約する。
