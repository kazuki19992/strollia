# 複数地点スポット(全地点を回って1スポット)設計

## 1. 目的と背景

日本三景のように「エリア全体」が名所になっているスポットは、全体を円で囲むと半径が数kmになり、近くを車で通過しただけで到達になってしまう。
そこで、展望台・観光案内所・寺社など、その名所を象徴する複数の地点をスポットに持たせ、**全地点を回ったら1スポットの到達(コンプリート)**として扱えるようにする。

観光案内所を地点に含められることも狙いの一つ。景色だけを見て帰る人にも案内所へ立ち寄る理由ができ、お土産購入などで地域にお金が落ちることを期待する(作り手の方針)。

最初の利用先は日本三景パック(松島・天橋立・宮島)。パックの具体的な地点選定は本設計の範囲外とし、別作業で行う。

## 2. ゴール / 非ゴール / アンチゴール

**ゴール**

- 1スポットに複数の到達エリア(以下「地点」)を持たせ、全地点の到達でスポット到達とする
- 途中経過を見せる(例: パック詳細で「松島 1/3」、どの地点が済んだか)
- 複数地点スポットのコンプリート時は、通常の「訪問済み」スタンプではなく専用の「コンプリート記念スタンプ」を表示する
- 既存の円1つのスポット(現在の全32件)は、データ・挙動・見た目とも変えない

**非ゴール**

- 「どれか1地点でよい」(any-of)の判定。今回は全地点必須(all-of)のみ
- スタンプへの日付・スポット名の差し込み(検討の結果やらないと決めた。スタンプは固定画像)
- 地点を回る順序の指定
- 日本三景パックのデータ作成

**アンチゴール(技術的に動いても失敗とみなすもの)**

- 既存ユーザーの到達記録・パック完走・滞在計測中の状態が、移行で失われたり変わったりする
- 円1つのスポットの到達タイミングや通知が変わる
- 地点の到達だけでスポット到達やパック完走が確定してしまう

## 3. 用語

| 用語         | 意味                                                                              |
| ------------ | --------------------------------------------------------------------------------- |
| スポット     | パックに属する到達対象。パックの完走判定の単位(従来どおり)                        |
| 地点         | スポットが持つ到達エリア(中心座標・半径・滞在時間)。複数地点スポットは2つ以上持つ |
| 地点到達     | 1地点で滞在時間を満たしたこと                                                     |
| コンプリート | 複数地点スポットの全地点に到達したこと。スポット到達と同じ意味                    |

## 4. データ(マスタ JSON)

`data/landmarks/landmarkSpots.json` のスポットに、任意の `areas` 配列を追加する。

- `areas` を持たないスポットは従来どおり `latitude` / `longitude` / `radiusMeters` / `dwellSeconds` を持つ(既存データは無変更)
- `areas` を持つスポットは、上記4項目を持たず、代わりに `areas`(2件以上)を持つ。スキーマで「どちらか一方」を強制する
- 各地点は `id`(UUIDv7、スポットIDと同じ形式)・`name`・`latitude`・`longitude`・`radiusMeters`・`dwellSeconds`・任意の `note` を持つ
- 地点名はスポット名を括弧で添える書き方にする(例: `観光案内所(松島)`)。表記はデータ側の責任とし、アプリで自動付与しない
- 地点のIDは到達記録に保存する安定識別子なので、一度リリースしたら変えない

**リリース後の変更ルール(既存のパック不変ルールの延長)**

- リリース済みの複数地点スポットに地点を追加・削除しない。追加すると、既にコンプリートしたユーザーとの整合が取れなくなる
- 地点を変えたい場合は、そのスポットを `retired` にして新しいスポットとして作り直す
- カタログ生成スクリプトで検証する項目: 地点IDの重複(スポットIDとの重複も含む)、`areas` 2件以上、地点の円が他のどの円(同じスポットの別地点・別スポットの地点・円1つのスポット)とも重ならないこと
- 円の重なり禁止は既存の方針(`landmarkCatalog.test.ts` の「異なるスポットの到達エリアの円が重ならない」)を地点へ広げたもの(設計者の判断)。到達判定は「範囲内で最寄りの1件だけを計測する」仕組みで、重なりがあると片方の計測が進まない・境界で入場時刻がリセットされるため。これにより判定ロジックと計測中状態の形(候補1件)を変えずに済む
- この制約のため、ある場所を「複数地点スポットの1地点」と「別パックの円1つのスポット」の両方に置くことはできない。将来は重なりを許容して並行計測する方向で別途設計する(issue #201)

## 5. 到達判定

判定の単位をスポットから**地点**へ一般化する。

- 円1つのスポットは「地点が1つで、その地点IDがスポットIDと同じ」ものとして内部で正規化する。これにより判定ロジックは1本で済み、既存の永続化された計測状態(`landmark_candidate_spot_id` にスポットIDが入っている)もそのまま地点IDとして読める
- 滞在の計測(入場時刻・外れ値の許容)は現行と同じ仕組みを地点単位で行う
- 到達済みの地点は判定対象から外す。到達済みのスポットに属する地点も外す
- 地点到達が確定したとき:
  - 円1つのスポット: 従来どおりスポット到達を記録する(地点の記録は作らない)
  - 複数地点スポット: 地点到達を記録し、同じトランザクション内でそのスポットの全地点が揃ったか確認する。揃った場合はスポット到達も記録する
- スポット到達の日時・ローカル日付・根拠GPSポイントは、最後の地点に到達したときのものを使う
- 地点到達は「一度到達したら取り消さない」(スポット到達と同じ方針)。何日かに分けて回ってもよい

## 6. 保存(DB)

- 新テーブル `landmark_area_visits` を追加する。列は `landmark_spot_visits` に揃え、`area_id`(主キー)・`spot_id`・`visited_at`・`visited_local_date`・`location_point_id`・`created_at` とする。挿入は `INSERT OR IGNORE`(初回の記録が正)
- `landmark_spot_visits` は無変更。パック完走・実績・通知の既存ロジックは引き続きこのテーブルを見る
- 計測中状態の列 `landmark_candidate_spot_id` は、意味を「計測中の地点ID」に広げる。列名の変更はしない(円1つのスポットでは地点ID=スポットIDのため互換)。コメントで意味を明記する
- 全データ削除(`logRepository` の `landmark_spot_visits` 削除箇所)では `landmark_area_visits` も一緒に削除する
- スキーマ変更手順は `db-schema-change` スキルに従う。`docs/data-storage.md` を更新する

## 7. 通知

- 円1つのスポット: 従来どおり(変更なし)
- 複数地点スポットの地点到達(コンプリート以外): 「〇〇(松島)に到達しました 1/3」のような途中経過の通知を出す(設計者の判断。回っている最中の楽しさを優先。うるさければ後で外せる)
- コンプリート時: 既存のスポット到達通知を出す。文言で「コンプリート」と分かるようにする
- パック完走の通知・実績は既存どおり、スポット到達をきっかけに評価する

## 8. 画面

**パック詳細画面(`LandmarkPackScreen`)**

- 複数地点スポットの行は、スポット名の横に進捗(`1/3` など)を表示する
- その行の下に、地点ごとの行を字下げして並べる。地点行には地点名と、到達済みなら到達日を出す(設計者の判断。どこが残っているか分からないと次に向かえないため)
- 地点行のタップ:
  - 到達済み: その日の日別記録詳細へ(スポット行と同じ動き)
  - 未到達: 埋め込み地図をその地点の円へズーム(スポット行と同じ動き)
- 複数地点スポットの行のタップ: コンプリート済みなら最後の地点の日の日別記録詳細へ、未コンプリートなら埋め込み地図を全地点が収まる範囲へズーム
- 複数地点スポットのスタンプは2段階にする(ユーザー指定、2026-11-10)。1地点でも到達していれば「訪問済み」スタンプ(1か所でも着いていれば訪問はしているため)、全地点に到達(コンプリート)したら「コンプリート記念スタンプ」に置き換える。未到達なら何も出さない。円1つのスポットは従来どおり「訪問済み」スタンプ
- 共通部品の新設・拡張は DESIGN.md と AGENTS.md §10.2 に従う(地点行は既存のリスト行の拡張を優先し、画面独自コンポーネントが必要なら理由を共有して承認を得る)

**埋め込み地図(`LandmarkPackMapPreview`)**

- 複数地点スポットは全地点の円を描く。到達済みの地点は到達済みスポットと同じ見た目にする
- 拡大時に出る名前・条件のラベルは地点単位で出す

**実績一覧のパック進捗**

- 分母・分子はスポット単位のまま(複数地点スポットはコンプリートして初めて1と数える)

## 9. コンプリート記念スタンプ

- 素材: ユーザー提供の `~/Downloads/completed_stamp.svg`(2026-11-10 にユーザーが添付した最新版。緑の円形スタンプ。「すとろりあ」「コンプリート記念スタンプ」の文字入り、300×300)。リポジトリへ取り込んで正式な素材とする
- 配置と形式は既存の「訪問済み」スタンプ(`assets/achievements/spots/spots-visited-stamp.png`)に揃える方向で builder が決める。ただし `assets/achievements/spots/svg/` はパックトロフィーのSVG置き場で、`generate:landmarks` が中の全SVGをPNG化するため、そこへ置く場合は生成物の扱いを確認すること
- 文字の差し込みはしない(固定画像)

## 10. テスト

AGENTS.md / `.ai/context/testing.md` に従い TDD で進める。最低限:

- カタログ生成: `areas` のスキーマ検証(片方だけ持つ、2件以上、ID重複)と、地点を含むすべての円の重なり禁止
- 到達判定: 地点単位の計測、到達済み地点の除外、円1つのスポットの挙動が従来と同じこと(既存テストがそのまま通ること)
- 記録: 途中の地点ではスポット到達が記録されない、最後の地点で同一トランザクション内にスポット到達が記録される、日時は最後の地点のもの、二重記録しない
- 移行: 既存DBにテーブルが追加され、既存の到達記録・計測中状態が保たれる
- 全データ削除で地点記録も消える
- 画面: 進捗表示、地点行、コンプリート記念スタンプ(円1つは訪問済みスタンプのまま)、タップ時の遷移とズーム
