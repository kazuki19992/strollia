# リリースノート作成

`main`(リリース済み)と `develop`(リリース予定)の差分から、ユーザー向けリリースノートを作成する。

## 手順

### 1. 差分の洗い出し

最新のリモート状態を取得してから、リリースに含まれる変更をすべて列挙する。

```bash
git fetch origin
git log origin/main..origin/develop --oneline --no-merges   # 個々のコミット
git log origin/main..origin/develop --oneline --merges       # マージされたPR一覧
```

PRタイトルだけで内容が判断できない場合は `gh pr view <番号>` で description を確認する。

### 2. 変更点リストの作成(中間成果物)

リリースノートを書く前に、**すべての変更を漏れなくリスト化**して分類する。このリストを先にユーザーへ提示する。

| 分類       | 基準                                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------------------- |
| 新機能     | ユーザーが新しくできるようになったこと(新画面・新設定・新通知など)                                   |
| 改善・修正 | ユーザーの見た目・操作・挙動が変わる改善やバグ修正                                                   |
| 内部変更   | ユーザーの動作に変化がないもの(リファクタリング、テスト、依存更新、CI、ドキュメント、ビルド設定など) |

分類に迷う判断基準: 「アップデート後にユーザーが気付ける変化か?」。気付けないものはすべて内部変更。

### 3. ユーザー向けリリースノートの生成

変更点リストをもとに、以下の形式で出力する。

```markdown
皆さんこんにちは！
このバージョンでは以下の変更が取り込まれています。

新機能

1. 【Plus限定】毎月1日の午前9時に「先月のレポートが完成しました！」という通知をお届けするようになりました。通知をタップするとそのまま月次レポート画面へ移動できます。
2. 設定画面に「よくある質問」を追加しました。
3. チュートリアルにエリアの説明ページを追加しました。（初回起動時にご確認いただけます）

改善・修正

4. Dynamic Islandにナビゲーション表示が出なくなりました。
5. GPXインポートが完了するまで操作ができないようにしました。
6. 【Plus限定】カスタム現在地アイコンがアプリ再起動後も正しく引き継がれるようになりました。
7. 設定画面にアプリのバージョンとビルド番号を表示するようになりました。（サポートお問い合わせ時にお役立てください）
8. その他の不具合修正やアプリ改善
```

### 4. アプリ内更新通知の候補作成と反映

リリースノートと同じ変更点リストから、工事看板風のアプリ内更新通知用に、短い要点を別途作成する。

- 最初にユーザーへ、このリリースでアプリ内更新通知を表示するか、初回起動では既存チュートリアルを優先して新規インストールへの通知を抑止するかを確認する。承認がなければ通知定義を更新しない
- 対象バージョンは、`package.json` と `app.json` で一致しているリリース予定版を使う。版番号が未確定なら推測せず、ユーザーへ確認する
- ユーザーが気付ける変更だけを候補にし、内部変更を除く。候補は重要度順にすべて `items` へ入れる
- 各 `item` は空文字を許可せず、`Array.from(text).length` で1文字以上20文字以内にする。UIは先頭2件だけを表示し、3件目以降があれば「など……」を自動表示する
- 新機能主体なら `kind: 'feature'`、修正主体なら `kind: 'fix'` を使う。見出し・節見出しはUIが `kind` から固定文言を導出する
- 過去の履歴は蓄積しない。`src/features/app-update/updateNotices.ts` の最新1件を、承認済みの版番号・文言で置き換える
- 定義がない版では起動時の更新通知を出さない安全側の実装を保つ

候補を次の形でユーザーへ提示し、**通知に載せる変更、重要順、対象版、種別**の承認を得る。ユーザーが「表示しない」と決めた場合も、`LATEST_UPDATE_NOTICE` を変更しない。**承認前にソースファイルを書き換えない。**

```ts
{
  version: '1.2.1',
  kind: 'feature',
  items: ['最重要の変更', '次に重要な変更', 'その他の変更'],
}
```

承認後に `src/features/app-update/updateNotices.ts` の最新定義を更新し、型チェックと関連テストを実行する。

## 書き方のルール

- **番号は「新機能」と「改善・修正」をまたいで通し番号**にする(markdownの番号リスト)
- 冒頭あいさつは「皆さんこんにちは！このバージョンでは以下の変更が取り込まれています。」で固定
- セクション見出しは「新機能」「改善・修正」の2つ。新機能がないリリースでは「新機能」セクションを省略してよい
- **内部変更はすべて最後の1項目「その他の不具合修正やアプリ改善」にまとめる**。個別に書かない
- Plus限定機能は文頭に **【Plus限定】** を付ける
- ですます調で、ユーザーが得られる価値・体験の変化として書く(実装の説明にしない)
- 内部用語・技術用語を出さない(`VisitedCell`→「エリア」、`SQLite`/`New Architecture`/ライブラリ名などは書かない)。文言は `src/ui/appText.ts` や画面上の表記に合わせる
- 補足があれば全角括弧で添える(例:（初回起動時にご確認いただけます）)
- SDKアップグレードやパフォーマンス改善など、ユーザーが体感し得るが説明しにくいものは「アプリの安定性・パフォーマンスが向上しました」のような体感ベースの表現にするか、「その他」へ含める

## 出力

1. 変更点リスト(分類付き)
2. ユーザー向けリリースノート(上記形式のmarkdown)
3. アプリ内更新通知の候補(対象バージョン、更新種別、重要順の要点一覧。見出しと「など……」はUIが導出)

の3つを順に提示する。リリースノートはそのままストアの「このバージョンの新機能」やリリースPRに転記できる状態にする。アプリ内更新通知の定義は、ユーザー承認後にだけ更新する。
