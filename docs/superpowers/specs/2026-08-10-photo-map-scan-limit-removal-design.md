# 写真マップ 表示上限撤廃(Phase 2)設計書

作成日: 2026-08-10
前提: Phase 1 設計書 `2026-08-10-photo-map-app-hang-design.md`
(App Hang 解消。PR #136 のブランチ `claude/fix-photo-map-app-hang` にあり、本ブランチには未マージ)

## 1. 目的

`DEFAULT_PHOTO_SCAN_LIMIT = 200` を撤廃し、**写真ライブラリ全体のジオタグ付き写真**を地図に表示できるようにする。

現状ユーザーは「最新200枚の中にジオタグがあるもの」しか見られず、過去の旅行の写真が地図に出ない。
これは記録を振り返るというアプリの中心的な価値を損なっている。

## 2. なぜ上限が外せなかったのか

`DEFAULT_PHOTO_SCAN_LIMIT = 200` は **3つの独立した問題を同時に隠している**。
1つでも残したまま上限を上げると、別の場所で破綻する。

| #   | 問題                                             | 箇所                                       | コストの性質                                |
| --- | ------------------------------------------------ | ------------------------------------------ | ------------------------------------------- |
| 1   | `getAssetInfoAsync` のメインスレッドJPEGデコード | `photoLibrary.ts` + ネイティブ             | **読み込み時** / N に比例・係数が非常に重い |
| 2   | クラスタリングが O(N²)                           | `photoClusters.ts` の `findNearestCluster` | **操作時** / パン・ズームごと               |
| 3   | マーカーのビューポート間引きなし                 | `MapScreen.tsx`                            | **描画時** / クラスタ数に比例               |

### 既に対応済みのもの

- **Phase 1(PR #136 / レビュー中)**: `getAssetInfoAsync` の並列数を 4 に制限し、App Hang を解消。
  ただしこれは**同時実行数の抑制であって総量の削減ではない**。N が増えれば総デコード回数はそのまま増える。
- **メモ化(PR #137 / レビュー中)**: パン時の再クラスタリングをスキップ。
  ただし Mercator 投影の影響で南北パンでは `latitudeDelta` が実際に変化するためミスしうる。
  また**ズーム時と写真追加時の O(N²) はそのまま残っている**。

> **依存関係**: #136 と #137 は本設計書の執筆時点で**まだ develop へマージされていない**。
> 本設計は両者のマージを前提とする(特に 2-a は #137 の `clusterMapPhotosByRadius` を、
> §4.0 は #136 の `PHOTO_INFO_CONCURRENCY` を前提にしている)。着手前にマージ状況を確認すること。

### 本設計書が扱う残りの課題

問題1の**総量**、問題2の**計算量そのもの**、問題3。

## 3. 最大の制約: 読み込みコスト

### 3.1 位置情報を取るためだけにフル解像度デコードが走る

`toMapPhoto`(`photoLibrary.ts`)が必要とするのは `location` / `id` / `uri` / `creationTime` / `width` / `height` のみ。

expo-media-library のネイティブ実装を確認した結果:

- `getAssetsAsync`(= `exportAsset`)は `id` / `uri` / `width` / `height` / `creationTime` を返すが **`location` を返さない**
- `location` を得るには `getAssetInfoAsync`(= `exportAssetInfo`)が必要
- `exportAssetInfo` 内で `location` は `asset.location` を読むだけの**同期プロパティアクセス**(I/Oもデコードもなし)
- しかし同じ関数が `requestContentEditingInput` の完了ブロック(**メインキュー**)で
  `CIImage(contentsOf:)` を呼び、**使いもしない EXIF のためにフル解像度 JPEG をデコードする**

ネイティブAPIは `getAssetsAsync` と `getAssetInfoAsync` の2つしかなく、
**位置情報だけを一括取得する手段は存在しない**(`MediaLibraryModule.swift` の `AsyncFunction` 定義を全て確認済み)。

EXIF 取得をスキップする JS 側オプションもない。ネイティブパッチによる根本解決は
Phase 1 で**保守コストを理由に不採用と決定済み**であり、本設計でも採らない。

### 3.2 結論: 総量を減らせないなら、繰り返す回数を減らす

デコード1回あたりのコストも、位置情報取得に `getAssetInfoAsync` が要ることも変えられない。
変えられるのは **「同じ写真を何度デコードするか」** だけである。

現状は**アプリを起動するたびに毎回200件をデコードし直している**。
結果をどこにも保存していないためである。

したがって本設計の中心は **SQLite への永続化と差分スキャン** になる。

## 4. 方針

### 4.0 基本設計: 走査済みの分だけ表示し、走査中だけ画面を止める

本設計の中核は2つの割り切りである。

1. **スキャン中は他の操作をさせない**代わりに、スキャンしていない間は常に快適に動く
2. **走査済みの写真は、走査が途中でも表示する**。走査は必ず新しい順に進むため、
   表示範囲は常に「最新から連続したK件」となり、現行の「最新200件」と同じ形のまま K が増えていく

```text
┌─ 通常時(いつでもアプリは快適に使える)────────────────────┐
│  走査済みアセット数 < 200 → 現行どおり最新200件から表示     │
│  走査済みアセット数 ≧ 200 → photo_assets から表示          │
│                              (走査が進むほど表示が増える)  │
│  ライブラリ末尾まで走査済み → 全件表示・デコード0回で高速    │
└────────────────────────────────────────────────────┘
        ▲                              │
        │ 完了 / 中断                    │ ユーザーが「読み込む」を選択
        │ (どちらでも走査済み分は残る)    ▼
┌─ 走査中(ブロッキングダイアログ)──────────────────────────┐
│  GPXインポートと同じ、閉じられないダイアログを表示            │
│  確定的な進捗バー(N / M)+ 中断ボタン                       │
│  画面操作はできない = メインスレッドをスキャンに集中できる     │
│  1ページごとに photo_assets へコミット(中断しても無駄にならない)│
└────────────────────────────────────────────────────┘

差分スキャン(新しく撮った写真)は上記と独立して起動時に走る。
バックログが未完了でも動くため、中断したままでも新しい写真はすぐ地図に出る。
```

**この設計が優れている理由**(当初案の「バックグラウンドでスキャンしながらアプリも使える」より良い):

1. **中途半端な劣化がない。** 当初案はスキャン中もアプリを使える代わりに、メインスレッドの
   デコード競合で地図がカクつくことを認めていた。「使えるが不快」という最も避けたい状態になる。
   ブロッキングにすれば、スキャン中は**スキャンだけに専念**でき、それ以外の時間は**常に快適**になる
2. **UIとDBの競合が消える。** 地図描画・クラスタ再計算・他のDB書き込みと同時に走らないため、
   処理が単純になり不確定要素が減る(なおメインキューのデコード自体は残るため、
   ブロックすれば速くなるわけではない。同時実行数4も維持する)
3. **フォールバックが優雅。** 未走査時は現状の挙動そのままなので、
   **どの段階でも今より悪くならない**。スキャンを一度もしなくてもアプリは普通に使える
4. **中断が無駄にならない。** 走査済みの分はそのまま表示に反映されるため、
   ユーザーは「途中まで読み込む」という選択を安心して取れる
5. **既存の実装パターンに乗れる。** GPXインポートが既に同じ形
   (`GpxImportProgressDialog` / `Dialog dismissible={false}` / `GpxImportInterruptedError`)を持っている
6. **電力方針の議論が不要になる。** バックログ走査は常に前面・ダイアログ表示中にのみ動く

**例外**: 起動時の差分走査(新しく撮った写真の取り込み)だけはダイアログなしで動く。
件数が少ない場合に限る措置であり、閾値は §4.2 で 50 件と定める。
「バックログ走査は必ずダイアログ内」「差分走査は少量なら無言」という二本立てである。

**重要な制約**: ダイアログでブロックしていても、**メインスレッドを飽和させてはいけない**。
進捗バーの更新と中断ボタンの反応にはメインスレッドが必要であり、
Sentry の App Hang 検知も画面がブロックされているかどうかは考慮しない。
したがって Phase 1 の `PHOTO_INFO_CONCURRENCY = 4` は**そのまま維持する**。

### 4.1 全体像

```text
初回スキャン(ユーザーが明示的に開始・ブロッキングダイアログ)
  → ライブラリをページングで走査
  → 各アセットの location を getAssetInfoAsync で取得(同時実行数4を維持)
  → ジオタグ付きのみ photo_assets テーブルへ保存
  → 以後この端末では二度とデコードしない

2回目以降の起動
  → photo_assets から読むだけ(デコード0回・現状より高速)
  → 前回スキャン以降に追加された写真だけを差分スキャン

地図描画(スキャン完了後)
  → ビューポート範囲で photo_assets を SQL 絞り込み
  → 空間グリッドで O(N) クラスタリング
```

### 4.2 読み込み: SQLite キャッシュ + 差分スキャン

`docs/photo-geotag.md` §9.1 に既に `photo_assets` テーブル案が存在し、
§10 にも「初回のみ写真ライブラリをスキャンする / 以後は差分更新する」と記載がある。
本設計はこの既定路線を具体化するものであり、新しい方針の導入ではない。

#### テーブル定義

`src/db/database.ts` の `initializeDatabase` へ追加する。

```sql
CREATE TABLE IF NOT EXISTS photo_assets (
  asset_id TEXT PRIMARY KEY,
  latitude REAL NOT NULL,
  longitude REAL NOT NULL,
  taken_at TEXT NULL,
  uri TEXT NOT NULL,
  width INTEGER NOT NULL,
  height INTEGER NOT NULL,
  last_seen_at TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_photo_assets_latitude_longitude
  ON photo_assets(latitude, longitude);

CREATE INDEX IF NOT EXISTS idx_photo_assets_taken_at
  ON photo_assets(taken_at);
```

#### 保存するメタデータの内容と不変性

| カラム                   | 内容                                           | 出どころ                              | 不変か                            |
| ------------------------ | ---------------------------------------------- | ------------------------------------- | --------------------------------- |
| `asset_id`               | 写真ライブラリ上のID(iOS: `localIdentifier`)   | `getAssetsAsync`                      | ✅ 安定                           |
| `latitude` / `longitude` | 撮影位置                                       | `getAssetInfoAsync`(`asset.location`) | ⚠️ **変更されうる**               |
| `taken_at`               | 撮影日時                                       | `getAssetsAsync`(`creationTime`)      | ⚠️ **変更されうる**               |
| `uri`                    | 表示用URI(iOS: `ph://…` / Android: `file://…`) | `getAssetsAsync`                      | ✅ 安定                           |
| `width` / `height`       | ピクセル寸法                                   | `getAssetsAsync`                      | ⚠️ 編集でトリミングされると変わる |
| `last_seen_at`           | 最後に走査で確認した日時                       | アプリ側                              | —                                 |

**「基本変更されない」は概ね正しいが、例外がある。** iOS 15 以降、写真アプリでユーザーが
**撮影日時と位置情報を編集できる**。また写真を編集(トリミング等)すると寸法が変わる。
いずれも `asset_id` は同じまま内容だけが変わるため、**アプリ側では検知できない**。

対応方針: Phase 2 では**編集の追従を実装しない**。実害は「地図上の位置が編集前のまま」に留まり、
検知には全件再走査(= 上限撤廃の目的と矛盾するコスト)が必要なため。
将来必要になれば、削除検知と合わせて「設定画面からの手動再スキャン」で対応する。

**`local_uri` は保存しない。** `getAssetInfoAsync` が返す `localUri`
(= `requestContentEditingInput` の `fullSizeImageURL`)は一時的なパスであり、
アプリ再起動をまたいで有効である保証がない。代わりに `getAssetsAsync` が返す
安定した `uri`(`ph://` / `file://`)を保存する。

> **検証済み(2026-08-23): `uri` 単独では描画できない。表示用URIは都度解決する。**
> React Native 0.86 には `RCTPhotoLibraryImageLoader` が存在しない(`RCTImageLoader.mm` の
> コメント内で名前が言及されているだけ)ため、`<Image source={{ uri: 'ph://…' }} />` は何も描画しない。
> 実機では「マーカーは正しい位置に出てクラスタ数も正しいのに、画像だけが白紙」として現れた。
>
> そこで `local_uri` は当初方針どおり**保存せず**、ビューポート検索の結果に対してのみ
> 表示用URIを都度解決する方式へ切り替えた(解決結果はセッション内のメモリキャッシュにのみ載せる)。
> 解決には SDK 57 のクラスベース新API `Asset#getUri()` を使う。旧API `getAssetInfoAsync` は
> `CIImage(contentsOf:)` によるフル解像度デコードを伴い、これが §3.1 の App Hang の原因であるため
> **表示のたびに呼んではいけない**。詳細は `docs/photo-geotag.md` §9.5。

その他:

- **ジオタグのない写真は保存しない**(`docs/photo-geotag.md` §9.1 の既定)
- 緯度経度の複合インデックスでビューポート絞り込み(`BETWEEN`)を効かせる。
  `visited_cells` の `idx_visited_cells_xy` と同じ考え方
- `taken_at` とそのインデックスは **GPSログとの時刻連動(`docs/photo-geotag.md` §7)の準備工事**。
  Phase 2 では絞り込みに使わないが、後から実装するときにスキーマ変更と再スキャンが不要になるよう
  最初から保存しておく

#### スキャン状態の管理: 「走査済みの時間窓」として持つ

走査は `creationTime` の降順(新しい写真 → 古い写真)で進む。
状態を「どこまで進んだか」ではなく **「どの時間範囲を走査済みか」** として持つと、
中断・再開・差分スキャンがすべて同じモデルで扱える。

`app_settings` に以下を保存する(`settingsRepository` を使う。AsyncStorage は使わない)。

| キー                         | 型     | 内容                                                          |
| ---------------------------- | ------ | ------------------------------------------------------------- |
| `photoScanWindowNewest`      | string | 走査済み時間窓の**新しい側**の境界(ISO 8601)。未走査なら null |
| `photoScanWindowOldest`      | string | 走査済み時間窓の**古い側**の境界(ISO 8601)。未走査なら null   |
| `photoScanReachedLibraryEnd` | bool   | 古い方向へ走査しきって**ライブラリの末尾に到達したか**        |
| `photoScanPromptShown`       | bool   | 「読み込む / あとで」ダイアログを提示済みか                   |

**件数はどれも `app_settings` に保存せず、都度導出する。** カウンタとして加算保持すると、
後述の再走査(タイ境界の再処理・中断ページの再処理)で二重計上され、
進捗バーと表示モード判定の両方が壊れるため。

用途によって導出元が異なるので混同しないこと。

| 値                     | 導出方法                                                                                           | 用途                                             |
| ---------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **走査済みアセット数** | `getAssetsAsync({ createdAfter: WindowOldest, createdBefore: WindowNewest, first: 1 }).totalCount` | **表示モードの判定**(現行経路 or `photo_assets`) |
| 保存済み写真数         | `SELECT COUNT(*) FROM photo_assets`                                                                | 地図に出る写真の件数表示                         |

表示モードの判定に `COUNT(*)`(= ジオタグ付きの保存件数)を使ってはいけない。
判定の根拠は「現行経路が走査する最新200**アセット**を包含するか」であり、
ジオタグ付き件数ではその保証が成立しない(後述)。

> **実装上の注意**: `settingsRepository` には `getBooleanSetting` / `getStringSetting` しかなく、
> **数値getterが存在しない**。本設計では数値をこのテーブルへ保存しないため追加は不要だが、
> 将来必要になった場合は `getNumberSetting` の追加が要る。

**走査済み時間窓 = `[photoScanWindowOldest, photoScanWindowNewest]`。**
この範囲の写真は `photo_assets` に反映済みであることを保証する。

**`WindowOldest === null` は「まだ1ページもコミットしていない」を意味する。**
初回走査は `WindowNewest` を先に書くため、1ページ目の途中で強制終了されると
`WindowNewest` だけが設定された中間状態になりうる。この状態の扱いを明示する。

| 状態                | 意味              | 走査                         | 表示モード判定                      |
| ------------------- | ----------------- | ---------------------------- | ----------------------------------- |
| 両方 null           | 未走査            | 初回走査                     | 現行経路                            |
| `WindowNewest` のみ | **1ページ目未完** | 初回走査をやり直す(述語なし) | **現行経路**(走査済み0件として扱う) |
| 両方あり            | 走査途中 or 完了  | バックログ走査               | 走査済みアセット数で判定            |

中間状態を「走査済み」と誤認すると、**空の `photo_assets` を表示して現行より狭くなる**。
判定は `WindowOldest === null` を最優先で見ること。

```text
古い ←────────────────────────────────────→ 新しい
     [    未走査    ][ 走査済み時間窓 ][ 新規追加分 ]
                    ↑                ↑
            WindowOldest      WindowNewest
```

#### なぜ「位置カーソル」ではなく「時刻」で持つのか

`getAssetsAsync` の `endCursor` はプラットフォームで意味が異なる(実装を確認済み)。

|         | `endCursor` の実体                                                             | 中断中にライブラリが変化すると                                                                                         |
| ------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| iOS     | **アセットID**(`MediaLibraryUtilities.swift:426` が `lastAsset?["id"]` を返す) | ID→index をクエリ時に解決するため位置ずれは起きない。ただし**カーソル対象が削除されると `CursorException` で失敗する** |
| Android | **位置インデックス**(`GetAssets.kt:42` が `assetsCursor.position` を返す)      | 先頭に写真が挿入されると**インデックスがずれ、未走査の写真を飛ばす**                                                   |

したがって位置ずれの問題は **Android 固有**であり、iOS の問題は「削除時に失敗する」ことである。
どちらもセッションをまたぐ再開には使えないため、時刻境界を採用する。

> 当初の草案では「iOS の `endCursor` はインデックスなので位置がずれる」と記載していたが、
> これは**事実誤認**だった。結論(時刻境界を使う)は変わらないが、根拠を実装の確認結果へ差し替えた。

#### 境界は必ず「1ms 外側」へ置く(タイ問題)

**ネイティブの述語は厳密比較である**(`MediaLibraryUtilities.swift:384,391` で確認)。

```swift
NSPredicate(format: "creationDate > %@", date)   // createdAfter
NSPredicate(format: "creationDate < %@", date)   // createdBefore
```

`creationTime` が同一の写真は珍しくない(連写、AirDrop や一括インポート、SNS保存、スキャン取り込み)。
境界に「最後に処理したアセットの `creationTime`」をそのまま入れると、
**同一時刻の兄弟アセットが恒久的に走査対象から外れる**。しかも `ReachedLibraryEnd` は
やがて true になるため、アプリは「全部読み込んだ」と誤認する。**発見不能な写真欠落**になる。

したがって境界は常に**1ms 外側**へ置く。

| 境界           | 設定値                                  | 効果                                                    |
| -------------- | --------------------------------------- | ------------------------------------------------------- |
| `WindowOldest` | 処理済み最古の `creationTime` **+ 1ms** | `createdBefore` で同一時刻の兄弟を取りこぼさない        |
| `WindowNewest` | 走査開始時刻 **− 1ms**                  | `createdAfter` で開始時刻ちょうどの写真を取りこぼさない |

代償として境界のアセットが再走査されるが、`photo_assets` は `asset_id` 主キーの UPSERT なので無害。
件数をカウンタではなく都度導出するのも、この再走査を無害にするためである。

**UPSERT の定義**(`photo_assets` への保存時):

```sql
INSERT INTO photo_assets (asset_id, latitude, longitude, taken_at, uri, width, height, last_seen_at, created_at, updated_at)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
ON CONFLICT(asset_id) DO UPDATE SET
  latitude = excluded.latitude,
  longitude = excluded.longitude,
  taken_at = excluded.taken_at,
  uri = excluded.uri,
  width = excluded.width,
  height = excluded.height,
  last_seen_at = excluded.last_seen_at,
  updated_at = excluded.updated_at
```

`created_at` は更新しない(初回保存時刻を保持する)。`visited_cells` の UPSERT と同じ方針。

#### 3種類の走査

| 走査                 | 条件                          | `getAssetsAsync` の指定       | 更新するもの                                                                       |
| -------------------- | ----------------------------- | ----------------------------- | ---------------------------------------------------------------------------------- |
| **初回**             | 窓が未設定                    | 指定なし(最新から)            | 開始時に `WindowNewest`、ページごとに `WindowOldest`                               |
| **バックログ**(再開) | `ReachedLibraryEnd === false` | `createdBefore: WindowOldest` | ページごとに `WindowOldest`。`hasNextPage === false` で `ReachedLibraryEnd = true` |
| **差分**             | 窓が設定済み                  | `createdAfter: WindowNewest`  | **完了時に** `WindowNewest`(中断時は更新しない)                                    |

**永続化のタイミングが要件である。**

- **初回走査**の `WindowNewest` は**開始前に、1ページ目より先に**書き込む。
  完了時に書くと、初回走査を中断したときに「窓が未設定」のまま残り、
  (a) 次回また初回走査としてゼロからやり直し、(b) 差分走査が永久に起動しない、という二重の不具合になる。
  初回走査では**開始時刻より新しい写真は存在しない**ため、先に書いても窓に未走査領域は生じない
- **差分走査**の `WindowNewest` は逆に**完了時にのみ**書き込む。
  差分走査は `(WindowNewest, now]` の範囲を新しい順に走査するため、
  開始時に `WindowNewest = now` としてしまうと、**中断時に範囲の古い側が未走査のまま
  「走査済み」と主張される**(= 歯抜けが生じ、本設計の前提が崩れる)。
  中断時は据え置き、次回の差分走査が同じ範囲をやり直す(UPSERT なので無害)
- `WindowOldest` は**初回走査とバックログ走査でのみ**、1ページ処理してコミットするたびに更新する。
  **差分走査では絶対に触らない。** 差分走査は窓の新しい側を扱うため、ここで `WindowOldest` を
  動かすと窓が最新側へ潰れ、バックログ全体が黙って放棄される
- `WindowOldest` は**古い方向へしか動かさない**。新しい方向への更新要求は異常として無視する
  (後述の `after` カーソル異常時に窓が壊れるのを防ぐ防御)
- **ページの `photo_assets` 書き込みと `WindowOldest` の更新は、同一の SQLite トランザクションで行う。**
  カーソルだけが先に永続化された直後にクラッシュすると、次回走査がそのページを飛ばし、
  **写真が永久に欠落する**。`app_settings` も同じ SQLite 上にあるため、
  `withExclusiveTransaction`(`src/db/database.ts`)で両方をまとめて更新できる。
  分けざるを得ない場合は**必ず写真データを先に永続化してからカーソルを進める**
  (二重処理は UPSERT で無害だが、飛ばしは回復不能)。
  クラッシュ境界のテストを §6 に置く
- 記録する `WindowNewest` は**壁時計の走査開始時刻**であり、最新アセットの `creationTime` ではない。
  ユーザーは写真アプリで撮影日時を過去へ書き換えられるため、アセット由来の値を使うと窓が破綻する

**当初案にあったバグ**: 単一の `lastScannedAt` で管理すると、
中断時にその値を更新した場合に**未走査の古い写真が永久にスキップされる**。
時間窓モデルでは新旧の境界が分離されているため、この誤りが構造的に起きない。

#### ページング: ラン内は `after` カーソル、再開時のみ時刻境界

**1ラン内のページ送りには `after` カーソルを使う。時刻境界は永続化とラン再開にのみ使う。**

時刻境界だけでページ送りすると**無限ループする**。同一 `creationTime` のアセットが
1ページ分を超えて連続した場合(連写や一括インポートで起こりうる)、
`createdBefore: T + 1ms` は毎回まったく同じページを返し、
`WindowOldest` も同じ値のまま更新されないため、走査が1件も前へ進まない。

したがって役割を分ける。

| 用途                   | 使うもの                        | 理由                                         |
| ---------------------- | ------------------------------- | -------------------------------------------- |
| **ラン内のページ送り** | `after`(前ページの `endCursor`) | 必ず前進する。同一時刻が連続しても停滞しない |
| **永続化(中断・再開)** | `createdBefore: WindowOldest`   | プロセスをまたいでも壊れない                 |

`WindowOldest` は1ページのコミットごとに「そのページの最古 + 1ms」へ更新する。
再開時はこの値で `createdBefore` を指定して新しいランを始め、以後はまた `after` で送る。
再開直後に同一時刻のタイグループが再走査されるが、UPSERT なので無害であり、
その後は `after` が前進を保証する。

**ランの述語はラン中ずっと固定する。** `createdBefore` はラン開始時に `WindowOldest` から
決めたら、ラン中は変更しない(`WindowOldest` の永続化は続けるが、クエリには反映しない)。
述語を毎ページ更新すると、`after` のカーソルアセットが述語の範囲外へ出てしまう。

これが重要なのは、iOS ネイティブが**カーソルを解決できなかったとき黙って先頭から返す**ためである
(`MediaLibraryUtilities.swift:462` の `cursorIndex == NSNotFound ? 0 : cursorIndex + 1`)。
エラーにならないので、気づかないまま1ページ目を無限に処理し続ける。

**カーソル異常時の扱い**:

| 事象                           | ネイティブの挙動                   | 対応                                                                             |
| ------------------------------ | ---------------------------------- | -------------------------------------------------------------------------------- |
| カーソルのアセットが削除された | `CursorException` を投げる(`:343`) | 現在の `WindowOldest` から新しいランとして再開                                   |
| カーソルが述語の範囲外         | **黙って先頭から返す**(`:462`)     | 上記の述語固定で発生させない。加えて `WindowOldest` の単調性ガードで被害を止める |

**Android の `after` は位置オフセットである**(`GetAssetsQuery.kt`)。ラン中に
iCloud / Google フォトの同期などでライブラリ先頭へ写真が挿入されると全オフセットがずれ、
**窓の内側にあるはずのアセットを取りこぼす**。数十分かかりうるランでは無視できない。

対応: ページごとに「今回のページの最新 `creationTime` が前ページの最古以下である」ことを確認し、
満たさない場合は異常としてランを打ち切り、`WindowOldest` から時刻境界で再開する。
Android 実機での検証を 2-c のリリース条件に含める(§6)。
取りこぼしが起きた場合の最終的な回復手段は設定画面の「写真を再読み込み」である。

**1ページの件数**: 100件とする。1ページあたりのコミット粒度(中断時に失われる作業量)と、
`getAssetsAsync` 呼び出し回数のバランスから決める。実機計測で調整してよい。

#### 中断中に新しい写真が追加された場合(差分スキャンとの関係)

**差分スキャンは、バックログが未完了でも独立して動く。** 両者は時間窓の反対側を扱うため衝突しない。

```text
起動時(写真表示ON)
  ├─ 窓が設定済みなら、まず差分スキャン(createdAfter: WindowNewest)
  │    → 新しい写真は少数なので短時間で終わる
  │    → WindowNewest を更新して窓を拡張
  │
  └─ バックログ(ReachedLibraryEnd === false)は自動では再開しない
       → 設定画面の「読み込みを再開」からユーザーが明示的に開始する
```

**差分走査の契機は「起動時」と「前景復帰時」の2つとする。**
起動時だけにすると、アプリを開いたまま写真を撮った場合に次回起動まで地図へ反映されない。
前景復帰時にも走らせることで、「撮ってからアプリに戻れば出ている」という体験になる。
契機の判定には、権限再確認(後述)と同じく `appState` の active 復帰を使う。

写真ライブラリの変更監視(`MediaLibrary.addListener`)は Phase 2 では使わない。
前景にいる間の即時反映まで追うと、走査の起動契機が増えて状態管理が複雑になるため。

これにより、**バックログを中断したままでも、新しく撮った写真は次に前景へ戻った時点で地図に出る**。
ユーザーが最も見たいのは直近の写真であり、
「バックログを終わらせないと新しい写真が出ない」という状態は避けなければならない。

**差分が大きい場合の扱い**: 長期間アプリを起動していないと差分が数千件になりうる。
差分件数が**50件**を超える場合は、黙って走らせず**まず「読み込む」/「あとで」を確認する**。
「読み込む」を選んだ場合のみブロッキングダイアログへ移行する(バックログ走査と同じ扱い)。
閾値以下ならダイアログなしで処理する。

閾値を 200 ではなく 50 にする理由: 200件の無言デコードは
**元の App Hang を起こしたのとまったく同じ負荷**である(§3)。同時実行数4で緩和されるとはいえ、
§4.0 が排除したい「使えるが不快」な状態を再現しかねない。
50件程度なら体感できる遅延にならず、通常利用(前回起動から数十枚追加)はほぼ全て収まる。

#### 窓より古い写真が後から追加された場合

**これは削除・編集とは別の問題であり、Phase 2 で対応が必要である。**

`creationTime` が `WindowOldest` より古い写真は、次の経路で日常的に発生する。

- 古い写真の AirDrop 受信
- バックアップからの復元
- 共有アルバムからの保存
- 紙焼き写真のスキャン取り込み(EXIF の撮影日時が保持される)

`ReachedLibraryEnd === true` になると、バックログ走査の起動条件が閉じ、
差分走査は `createdAfter: WindowNewest` しか見ない。したがって
**どの経路からも到達できない写真**になる。

対応: **設定画面の行を完了後も消さない。**

- 未完了時: 「すべての写真を読み込む」 / 「写真の読み込みを再開(1,240 / 8,300)」
- **完了後**: 「写真を再読み込み」(常時表示)

押すと `WindowOldest` を無視した再走査を行い、窓を古い側へ広げ直す。
`photo_assets` は UPSERT なので既存分は上書きされるだけで無害であり、
将来の削除検知・編集追従の受け皿にもなる。

#### `creationTime` が null のアセット

iOS の `PHAsset.creationDate` は optional であり、`taken_at TEXT NULL` もそれを前提にしている。
`NSPredicate` の比較は null に対して常に false を返すため、
**`createdBefore` / `createdAfter` を指定したどの走査からも見えない**。

ここには「初回走査を中断すると再開経路では拾えない」という穴がある。
初回走査は述語なしで最新から進むが、null 日付アセットへ到達する前に中断すると、
以後の再開はすべて `createdBefore` 付きになるため**二度と現れない**。
「中断しても再開すれば全部読み込める」という本設計の約束と矛盾する。

対応: **null 日付アセット専用の走査フェーズを持つ。**

- `photoScanNullDateCompleted`(bool)を別に持ち、null 日付の走査完了を独立して管理する
- `getAssetsAsync` を**述語なし**(時刻境界なし)で走査し、`creationTime` が null のものだけ保存する
- バックログがライブラリ末尾へ到達したあと、このフェーズを実行してから
  `photoScanReachedLibraryEnd = true` とする
- 中断された場合も `photoScanNullDateCompleted` は false のままなので、
  「写真を再読み込み」および再開経路からやり直せる

**このフェーズを省く場合は、null 日付アセットが対象外であることを設計と UI 文言に明記すること。**
黙って落とすのが最も悪い。撮影日時を持たないアセットは稀だが、
「全部読み込んだはずなのに出ない写真がある」は原因の特定が極めて困難になる。

**削除された写真の扱い**: `last_seen_at` を持たせるが、Phase 2 では削除検知を実装しない。
削除済みアセットは `uri` の解決に失敗して表示されないだけで実害が小さく、
全件突合はライブラリ全体の再走査を意味するため上限撤廃の目的と矛盾する。
必要なユーザーは上記「写真を再読み込み」を使える。

#### 表示するのは「走査済みの写真」: 部分スキャンもそのまま活きる

走査は**必ず新しい順**に進む。したがって走査済みの集合は常に
**「最新から連続した K 件」**という形になり、歯抜けが生じない。

これは現行の「最新200件」と**同じ形のまま K が増えていくだけ**であり、
ユーザーから見た挙動は完全に予測可能である。「8割スキャンしたのに200件しか出ない」も起きない。

| 状態                       | 表示                                                          |
| -------------------------- | ------------------------------------------------------------- |
| 一度も走査していない       | 現行の `loadGeotaggedPhotos(200)`(= アップデート前と同じ挙動) |
| 走査済みアセット数 < 200   | 同上(現行経路のほうが広いため)                                |
| 走査済みアセット数 ≧ 200   | `photo_assets` から表示(走査が進むほど増える)                 |
| ライブラリ末尾まで走査済み | `photo_assets` から全件表示                                   |

判定に使うのは**走査済みアセット数**であり、ジオタグ付きの保存件数ではない。

```text
scannedAssetCount = getAssetsAsync({
  createdAfter: WindowOldest,
  createdBefore: WindowNewest,   // 窓の外(未走査の新着)を数えないため必須
  first: 1,
}).totalCount

// WindowOldest === null(1ページ目未完)の場合は 0 として扱う
```

**ジオタグ付き件数で判定してはいけない。** ジオタグ率の低いライブラリ
(例: 4万枚中ジオタグ付き60枚)では件数が永久に200へ届かず、
**フルスキャンを完了させたのに現行経路のまま = 機能が何もしない**という事態になる。
ブロッキングスキャンを課したうえで成果ゼロは最悪の結果である。
`ReachedLibraryEnd === true` のときは件数に関わらず `photo_assets` を使う(表の4行目が優先)。

**判定の根拠**: 現行経路は「最新200**アセット**」を走査する。したがって
走査済みアセット数が200以上であれば、`photo_assets` は現行経路が見つけるものを包含する。
走査済みが200未満なのは初回走査の開始直後(と、そもそも200枚未満のライブラリ)だけであり、
そこでは現行経路にフォールバックするため今より狭くならない。

#### 例外: 時間経過で現行経路より狭くなりうるケース

上の包含関係は**走査時点のスナップショット**についてのものである。
以下は設計として認識しておく必要がある。

| 例外                                | 内容                                                                                                                             | 対応                       |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| 一時的な取得失敗                    | `getAssetInfoAsync` が失敗したアセットは保存されない。現行経路は毎起動リトライするが、走査済み窓は先へ進むため**恒久的に欠ける** | 「写真を再読み込み」で回収 |
| 後からジオタグ付与                  | 走査後に写真アプリで位置情報を付けた写真は、窓の内側にあるため再走査されない                                                     | 同上                       |
| **権限のフルアクセス→限定への降格** | `photo_assets` に残った行を表示し続ける。`docs/photo-geotag.md` §11「権限が取り消された場合は写真表示を停止する」に**違反する**  | **必須対応**(下記)         |

**権限降格への対応は必須とする。** これは表示範囲の問題ではなくプライバシー要件違反である。

確認の契機は起動時と写真表示ON時だけでは足りない。**アプリ使用中に設定アプリで権限を変更され、
前景へ戻ってくる**経路があるためで、この間キャッシュ済みの `photo_assets` が
`MapScreen` と `PhotoClusterMarker` へ供給され続けてしまう。

以下すべての契機で `hasFullPhotoAccess`(`photoLibrary.ts`)を再確認する。

| 契機                     | 実装の足がかり                                                               |
| ------------------------ | ---------------------------------------------------------------------------- |
| 起動時                   | `useAppInitialization`                                                       |
| 写真表示を ON にしたとき | `usePhotoMapCrashBreaker.updateShowPhotosOnMap`                              |
| **前景復帰時**           | `useLocationRecordingSync` が公開する `appState`(既存の AppState 監視を流用) |
| **走査中の失効**         | 各ページ処理の前に確認し、失効していたら走査を中断する                       |

フルアクセスでなくなっていた場合は、`photo_assets` の**検索も表示も停止する**
(取得してから捨てるのではなく、クエリ自体を実行しない)。

上限撤廃は「やれば良くなる」オプトイン機能として位置づける。

#### スキャン中: GPXインポートと同じブロッキングダイアログ

既存の `GpxImportProgressDialog`(`Dialog dismissible={false} swipeToClose={false}`)と同じ形式にする。

- 閉じられないダイアログで**画面操作を止める**
- **確定的な進捗バー**を表示する(「写真を読み込んでいます… 1,240 / 8,300」)。
  分母は**そのランの開始時点で走査対象となるアセット総数**
  (バックログなら `getAssetsAsync({ createdBefore: WindowOldest, first: 1 }).totalCount`)を
  ラン開始時に一度だけ取得して固定する。ページごとに取り直すと `createdBefore` が進むたびに
  分母が縮み、バーが逆走して見える。
  GPXインポートは総数が事前に分からないため `IndeterminateProgressBar` を使っているが、
  写真スキャンは `getAssetsAsync` の `totalCount` で総数が取れるため確定的なバーにできる
- **中断ボタン**を併設する
- 1ページ処理するごとに `photo_assets` へコミットするため、中断しても読み込み済みの写真は残る
- 同時実行数は Phase 1 の 4 を維持する(§4.0 の制約。進捗バーと中断ボタンの応答性を守るため)

**中断時の挙動**:

- 処理中のページをコミットしてから停止する
- コミットした範囲まで `photoScanWindowOldest` を進める
- `photoScanReachedLibraryEnd` は **false のまま**にする(上記の状態機械に従う)
- **走査済みの写真はそのまま地図に表示され続ける**(前項「表示するのは走査済みの写真」)

#### 既存のクラッシュブレーカーとの干渉(要対応)

`usePhotoMapCrashBreaker`(`src/ui/hooks/usePhotoMapCrashBreaker.ts`)は、
写真表示の有効化時に `showPhotosOnMapEnablePending` を立て、
**写真読み込みとマーカー描画が2秒安定してから**解除する(`:201-213`)。
次回起動時に pending が残っていれば「前回クラッシュした」と判断し、
**写真表示を自動でOFFへ戻す**(`:230-236`)。

長時間のブロッキングスキャンは、**OSによる強制終了・メモリ逼迫・自動ロック後の suspend が
最も起きやすい操作**である。ここで pending が残ったまま終了すると、次回起動時に
写真表示がOFFにされる。写真表示がOFFになるとダイアログも出ないため、**対策を講じなければユーザーは復帰手段を失う**
(この危険を踏まえて、後述のとおり設定画面の行は写真表示がOFFでも表示する)。

対応:

1. **スキャン開始前に pending が解除済みであることを必須条件にする。**
   写真表示が安定して動いている状態からのみスキャンを開始できるようにし、
   「有効化直後の不安定な状態で長時間処理へ入る」経路を塞ぐ。
   pending は写真描画が2秒安定してから解除されるため、トグルON直後に「読み込む」を押した場合は
   **解除まで開始を待つ**(ボタンを無効化せず、押した操作は保持して解除後に自動で開始する)
2. **スキャン状態を `showPhotosOnMap` から独立させる。**
   仮に写真表示がOFFへ戻されても `photoScanWindow*` は保持されるため、
   ユーザーが写真表示を再度ONにすれば読み込み済みデータがそのまま活きる
3. **設定画面の行は `showPhotosOnMap` の値に関わらず表示する。**
   OFFのときは「写真表示をONにしてください」と案内し、行き止まりを作らない

§5 の変更対象に `usePhotoMapCrashBreaker.ts` を含める。

#### 所要時間の見積もりと画面ロック

**この設計の成否は所要時間に依存するため、実装前に実測が必要である。**

Phase 1 の分析より、支配的なコストはメインキューでのフル解像度JPEGデコードである。
1件あたりのデコードを仮に 100〜300ms とすると、同時実行数4では:

| ライブラリ規模 | 概算所要時間(1件200ms・並列4で試算) |
| -------------- | ----------------------------------- |
| 2,000枚        | 約 1.7 分                           |
| 10,000枚       | 約 8 分                             |
| 40,000枚       | 約 33 分                            |

**この数字は未実測の試算であり、実機で測るまで信用してはならない。**
数十分かかることが判明した場合、「一度に全件を読み込む」前提そのものを見直す必要がある
(例: 直近1年分だけ読む選択肢を用意する)。§6 の実機確認を**設計の妥当性検証**として扱う。

**画面ロック対策**: 数分以上かかる操作中に iOS の自動ロックが働くとアプリが suspend され、
上記のクラッシュブレーカー問題を誘発する。スキャン中は `expo-keep-awake` で
画面ONを維持する。既に `KEEP_AWAKE_TAG`(`AppStateProvider.tsx`)で同モジュールを使っており、
別タグで併用できる。

#### スキャン開始のタイミング: 常にユーザーの明示的な選択

**バックログ走査を自動で始めることはしない。** 重い処理かつ画面をブロックするため、必ず選択させる。
(起動時の差分走査は例外。50件以下なら無言で処理する。前述「差分が大きい場合の扱い」)

| ユーザーの状態                      | 判定条件                                                                                                            | 挙動                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 写真表示が OFF                      | `showPhotosOnMap === false`                                                                                         | 何もしない。スキャンもダイアログも出さない         |
| **写真表示を ON にした**            | トグル操作時に `photoScanReachedLibraryEnd !== true`                                                                | **「読み込む」/「あとで」ダイアログ**を出す        |
| **既存ユーザーで写真表示が既に ON** | 起動時に `showPhotosOnMap === true` かつ `photoScanReachedLibraryEnd !== true` かつ `photoScanPromptShown !== true` | **起動時に同じダイアログ**を出す                   |
| 走査済み(バックログ完了)            | `photoScanReachedLibraryEnd === true`                                                                               | 差分スキャンのみ(§4.2。閾値以下ならダイアログなし) |

2行目・3行目のどちらでも**同じダイアログ**を使う。伝える内容:

- 全ての写真を地図に表示できるようになったこと
- そのために一度だけ写真の読み込みが必要で、**その間は画面を操作できない**こと
- いつでも中断でき、続きから再開できること
- 「あとで」を選ぶと**最新200件の中のジオタグ付き写真のみ**が表示されること

選択肢: **「読み込む」/「あとで」**

- 「読み込む」→ ブロッキングダイアログへ移行しスキャン開始
- 「あとで」→ 走査は始めず現行どおり最新200件から表示する。**写真表示自体は ON になる**

**`photoScanPromptShown` は、どちらを選んでもダイアログを閉じた時点で true にする。**
「読み込む」を選んで途中で中断した場合に、次回起動でまた同じ確認が出るのを防ぐため。
中断後の再開は設定画面から行う(次項)。

| 選択     | `photoScanPromptShown` | その後                                               |
| -------- | ---------------------- | ---------------------------------------------------- |
| 読み込む | true                   | ブロッキングダイアログへ移行。中断しても再表示しない |
| あとで   | true                   | 走査せず現行表示のまま。再表示しない                 |

このフラグはダイアログの再表示抑止のみに使い、**走査の進捗状態とは独立**させる
(走査状態は `photoScanWindow*` / `photoScanReachedLibraryEnd` が持つ)。

#### 設定画面からの開始・再開

設定画面のプライバシー/写真セクションへ、**常に**行を出す。状態でラベルを変える。

| 状態                                   | ラベル                                                         |
| -------------------------------------- | -------------------------------------------------------------- |
| 未着手                                 | 「すべての写真を読み込む」                                     |
| 中断済み                               | 「写真の読み込みを再開(1,240 / 8,300)」                        |
| 走査完了(`ReachedLibraryEnd === true`) | 「写真を再読み込み」                                           |
| 写真表示が OFF                         | 「すべての写真を読み込む」(押下時に写真表示をONにするよう案内) |

**完了後もこの行を消してはいけない。** 以下4つの回復手段がすべてこの行に依存している。

1. 走査完了後に追加された古い写真の取り込み(前述)
2. 一時的な取得失敗で欠けた写真の回収(後述の「例外」)
3. 走査後にジオタグを付けた写真の取り込み(同上)
4. `creationTime` が null のアセットの回収(前述)

写真表示が OFF のときも行を残す。クラッシュブレーカーが写真表示を自動OFFへ戻した場合に
ユーザーが行き止まりにならないようにするため(前述「既存のクラッシュブレーカーとの干渉」)。

**押したときの挙動は写真表示の状態で分ける。**

| 写真表示 | 押下時の挙動                                                                      |
| -------- | --------------------------------------------------------------------------------- |
| ON       | そのままブロッキングダイアログへ移行して走査を開始・再開する                      |
| OFF      | **走査は開始しない。** 「マップ上に写真を表示」をONにするよう促すダイアログを出す |

OFF のまま走査を始めない理由は、§4.2 の「写真表示が OFF なら何もしない」と一貫させるため。
勝手に写真表示をONへ切り替えるのは、センシティブな権限を伴う設定の暗黙変更にあたるため避ける。

### 4.3 操作: クラスタリングを O(N) へ

`findNearestCluster`(`photoClusters.ts`)は既存クラスタを全走査するため O(N × C)、
写真が散在する実データでは C ≒ N となり実質 O(N²)。

**空間ハッシュ**へ置き換える。セルサイズ = クラスタ半径とし、
各写真を自セルと周囲8セルのみと比較する。比較対象が定数個に収まるため O(N) になる。

| 写真数 | 現状 O(N²) | 空間ハッシュ O(N) |
| ------ | ---------- | ----------------- |
| 200    | 約 4万     | 約 200            |
| 5,000  | 約 2,500万 | 約 5,000          |
| 20,000 | 約 4億     | 約 20,000         |

既存の `src/features/location/grid/gridCell.ts` の `coordinateToGridCell` と同じセル座標の考え方を流用できる。

**重要な制約**: 現在の `findNearestCluster` は「クラスタ代表点との距離のみを見る」ことで
連鎖的な巨大クラスタ化を防いでいる(`photoClusters.ts` のコメントに明記)。
この性質は空間ハッシュ版でも維持する。既存テスト
「連鎖的に離れた写真を巨大クラスタにまとめない」がそのまま回帰テストとして機能する。

**半径の量子化**: メモ化(PR #137)は `latitudeDelta` が bit 単位で一致することを前提にしており、
Mercator 投影の影響で南北パンでは一致しない。半径を離散段階へ丸めることでこれを解消する。
`gridAggregation.ts` の `getStableDisplayCellSizeMeters`(ヒステリシス付き段階制)が既に同じ問題を
解いているので、同じパターンを踏襲する。

### 4.4 描画: ビューポート絞り込み

現状 `clusterMapPhotos` はビューポート外の写真も全て対象にし、`MapScreen.tsx` は
クラスタ数だけマーカーを描画する(間引きなし)。

- クラスタリング**前に** SQL で絞り込む(`WHERE latitude BETWEEN ? AND ? AND longitude BETWEEN ? AND ?`)
- **経度180度線をまたぐ場合は `BETWEEN` が空集合を返す**(min > max になるため)。
  既存の `getGridBoundsForRegion`(`src/features/location/grid/gridCell.ts`)が
  `crossesAntimeridian` を扱っているので、同じ判定を写真側にも適用し OR 条件へ分岐させる
- 余白は `GRID_OVERLAY_CONFIG.boundsPaddingRatio` と同様に表示範囲の外側へ持たせ、
  小さなパンで再取得が走らないようにする
- これにより、ライブラリに何万枚あっても**JS へ載るのは画面周辺の写真だけ**になる

この絞り込みが入ると、4.3 の O(N) 化における N も「画面内の写真数」に縮む。

## 6. テスト方針

`AGENTS.md` §2 / §9 に従い、端末APIそのものではなく分離した純粋ロジックをテストする。

### 純粋関数(重点)

- **空間ハッシュクラスタリング**: 既存 `photoClusters.test.ts` の全ケースが通ること(挙動不変の保証)。
  加えて「連鎖的に離れた写真を巨大クラスタにまとめない」性質が保たれること。
  現行 O(N²) 実装と同一入力で**同じクラスタ結果になる**ことを比較テストで固定する
- **半径の量子化**: 隣接する `latitudeDelta` が同じ段階へ丸められること。境界でのヒステリシス
- **ビューポート範囲計算**: 余白込みの緯度経度境界が正しいこと

### リポジトリ

`db` をモジュールモックする(`.ai/context/testing.md` のパターン)。

- ジオタグなしアセットが保存されないこと
- 同じ `asset_id` の再スキャンで重複行が増えないこと(UPSERT)
- ビューポート検索が範囲外の写真を返さないこと
- `deleteAllUserData` が `photo_assets` も削除すること

### スキャン状態の状態機械(重点・純粋関数)

**ここが本設計で最もバグを埋め込みやすい箇所**であり、純粋関数へ切り出して重点的にテストする。

- バックログ走査は `createdBefore: photoScanWindowOldest` を指定すること
- 差分走査は `createdAfter: photoScanWindowNewest` を指定すること
- **`WindowOldest` が「処理済み最古の creationTime + 1ms」であること**
  (同一 `creationTime` の兄弟アセットを取りこぼさないための境界。ネイティブ述語が厳密比較のため必須)
- **`WindowNewest` が「走査開始時刻 − 1ms」であること**
- **`WindowNewest` が1ページ目より前に永続化されること**
  (初回走査を中断したときに窓が未設定のまま残ると、差分走査が永久に起動しない)
- `WindowOldest` が1ページごとに更新されること(完了時ではない)
- `WindowNewest` がアセット由来ではなく**壁時計の走査開始時刻**であること
- **差分走査を中断したとき `WindowNewest` が更新されないこと**
  (更新すると差分範囲の古い側が未走査のまま「走査済み」と主張され、歯抜けが生じる)
- **同一 `creationTime` のアセットが1ページを超えて連続しても走査が前進すること**
  (時刻境界だけでページ送りすると無限ループする。ラン内は `after` カーソルを使う根拠)
- 表示モード判定に使う件数が**アセット数**であり、`COUNT(*)`(ジオタグ付き件数)ではないこと
- **中断時に `photoScanWindowNewest` を書き換えないこと**(古い写真の恒久スキップを防ぐ回帰テスト)
- **中断時に `photoScanReachedLibraryEnd` を true にしないこと**
- ライブラリ末尾に到達したときだけ `photoScanReachedLibraryEnd = true` になること
- `photoScanWindowNewest` に記録するのが走査**開始**時刻であること(走査中に撮影された写真を取りこぼさない)
- **バックログ未完了でも差分走査が実行できること**(両者が独立していることの回帰テスト)
- 差分件数が閾値を超える場合にブロッキングダイアログを要求する判定になること

### 表示モードの判定(純粋関数)

- 一度も走査していない → 現行経路(`photo_assets` を参照しない)
- 走査済み**アセット**数 < 200 → 現行経路のまま(**今より狭くならない**ことの回帰テスト)
- 走査済み**アセット**数 ≧ 200 → `photo_assets` から表示
- **ジオタグ付き件数が200未満でも、走査済みアセット数が200以上なら `photo_assets` を使うこと**
  (ジオタグ率の低いライブラリで機能が無効化される不具合の回帰テスト)
- `ReachedLibraryEnd === true` なら件数に関わらず `photo_assets` を使うこと
- **フルアクセスでない場合は `photo_assets` を検索も表示もしないこと**(プライバシー要件)
- **前景復帰時に権限を再確認すること**(使用中に設定アプリで降格された場合の検知)
- **部分スキャンでも走査済みの写真が表示されること**(中断が無駄にならないことの保証)

### ダイアログ表示タイミングの判定(純粋関数)

- 写真表示 OFF → スキャンもダイアログも発生しない
- 写真表示を ON にした & 未スキャン → ダイアログを出す
- 起動時に写真表示 ON & 未スキャン & プロンプト未表示 → ダイアログを出す
- 「あとで」選択後 → 再表示しない
- **「読み込む」を選んで中断した後も再表示しない**(`photoScanPromptShown` は両分岐で true)
- スキャン完了済み → ダイアログを出さない
- 写真表示 OFF で設定画面の行を押した場合 → 走査を開始せず、写真表示ONを促すこと

### スキャナ(サービス層)

`MediaLibrary` をモックする。

- 初回は最新から走査し、再開時は `createdBefore` 付きでバックログのみ走査すること
- 中断後の再開で、**境界のタイグループを除き**、既に保存済みのページを再走査しないこと
  (境界の同一 `creationTime` グループは仕様上あえて再走査する。§4.2「境界は必ず1ms外側へ置く」)
- **中断してから再開したとき、中断前より古い写真も最終的に全て保存されること**
  (状態機械のバグを結合レベルでも捕まえる)
- **中断中に写真が追加されても、差分走査でその写真が保存されること**
  (バックログ未完了でも新しい写真が出ることの保証)
- **中断中に写真が追加・削除されても、未走査の写真がスキップされないこと**
  (位置カーソルではなく時刻境界を使う理由そのものの回帰テスト)
- **同一 `creationTime` のアセットがページ境界・中断点にまたがっても、全て保存されること**
  (境界を1ms外側へ置く理由そのものの回帰テスト。burst撮影・一括インポートで日常的に起きる)
- **走査完了後に `WindowOldest` より古い写真が追加された場合、「写真を再読み込み」で取り込めること**
- 表示モード判定の件数が `getAssetsAsync().totalCount`(アセット数)から導出され、
  `COUNT(*)`(ジオタグ付き保存件数)ではないこと
- 件数がカウンタ保持ではなく都度導出で、再走査しても二重計上されないこと
- 中断シグナルを受けたら、処理中のページをコミットしてから停止すること
- **ページの保存とカーソル更新が同一トランザクションであること。**
  カーソル更新後・ページ保存前にクラッシュした状況を模し、
  再開後にそのページの写真が欠落しないことを検証する
- **null 日付アセットの走査フェーズが、バックログ完了後に実行されること。**
  初回走査を早期に中断してから再開しても、最終的に null 日付アセットが保存されること
- **走査中に権限がフルアクセスでなくなったら、走査を中断すること**
- 同時実行数が `PHOTO_INFO_CONCURRENCY` を超えないこと(Phase 1 の回帰を維持)

### プラットフォーム別の実機確認(2-c のリリース条件)

- **iOS**: 初回走査の所要時間実測(§4.2 の試算の検証)。自動ロック中断が起きないこと
- **Android**: `after` が位置オフセットであることに起因する取りこぼしが起きないこと。
  走査中に写真が同期・追加される状況を作って検証する

### テストで担保できない部分

- 実機での初回スキャン所要時間と発熱・バッテリー影響
- 大量マーカー描画時の実際のフレームレート

いずれも development ビルドでの手動確認とする。**ジオタグ写真が数千枚あるライブラリでの
実機確認を、上限撤廃のリリース条件とする**。

## 7. 影響範囲とリスク

### ユーザー向け

- **利点**: ライブラリ全体のジオタグ写真が地図に出る。2回目以降の起動は現状より**速くなる**(デコード0回)
- **初回のみ**: スキャンに時間がかかる。進捗表示と段階的表示で体験を担保する
- 写真表示 OFF のユーザーには一切影響しない(スキャンも走らせない)

## 8. 段階リリース

1つのPRで全部やらない。各段階が単独で意味を持ち、単独でリリースできる形にする。

| 段階    | 内容                                                                                           | 単独での価値                                                   |
| ------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **2-a** | クラスタリングの O(N) 化 + 半径の量子化                                                        | 上限そのままでも、ズーム時の再計算とパンのメモ化ミスが軽くなる |
| **2-b** | `photo_assets` テーブル + リポジトリ + ビューポート絞り込み                                    | 描画対象が画面周辺だけになる                                   |
| **2-c** | ページング走査 + 差分スキャン + ブロッキングダイアログ + 中断/再開 + モード切替 + **上限撤廃** | 全写真が地図に出る                                             |

**2-c が本命だが、2-a と 2-b が入っていないと 2-c で破綻する。** この順序は前後できない。

各段階の詳細計画は、着手時に個別の計画書として起こす。
2-c は範囲が大きいため、着手時にさらに分割する可能性がある。
